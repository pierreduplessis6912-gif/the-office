## 12. Creating a new customer's business

A business is created by **you**, not by self-serve sign-up (decided 2026-10-14). It needs three things: a **business id** (3 to 40 lower-case letters, digits and hyphens, for example `acme-floors`), the **business name** as it should appear, and the **owner's Google email**, the account they will sign in with.

1. GitHub, Actions, **"Production new business"**, Run workflow. Fill the four boxes: the id, the name, the owner's email, and **the id again** in `confirm`.
2. It first **reads** the directory and asks whether that email already belongs to a business. A small script then decides. It **refuses**, before any write and with the run going red, when: the id is not valid or is reserved (`admin`, `api`, `app`, `auth`, `debug`, `demo`, `health`, `office`, `staging`, `test`, `www`, or starting `staging-`); the name or email is not valid; the id is not typed again exactly; **the email already belongs to another business** (one email can sign in to only one business; it does not say which); or **the business already exists and already has members** (so a typed id can never add a second owner to a live business; to add someone use `add-member`, section 8).
3. If it is allowed, it makes **one** attempt to create the business on the `standard` plan (100 messages per member per day, 400,000 neurons per business per day, enforced) with the owner as its owner. It then checks the result: the business is in the directory, active, on the standard plan; the owner is a member; its own object answers **as itself**. A failed check turns the run red.
4. **If it stops half way**, run it again with the **same boxes**: a business that exists with **no** members is completed; one that has members is refused.
5. Then tell the owner to install the app and **sign in with Google using exactly that address**. Their journey (business details, customers, invoices, team, suppliers, materials) starts the first time they open it, and each import step takes a spreadsheet.

**The owner's email is personal data and this repository is public, so it must never reach a log.** GitHub prints every step's `env:` block in its log, so the workflow keeps the email OUT of the environment and every expression: its first step reads it from the event file, registers it as a mask (any later print shows `***`) and writes it to a file the other steps read. The summary shows it only as `o***@acme.co.za`; the record (`ops/production-new-business-last.json`) holds the business id, its name and statuses only. **Verified, not assumed:** the first version had the email in the environment and it appeared 10 times in one run's logs; after the fix a canary address appears 0 times in 11 log files (the tool below). **Never type a real email address into the leak-check workflow.** It is a check for PLACEHOLDERS.

**What it does not do:** it sends no invitation (you tell the owner); there is **no workflow to delete a business**, so a business created by mistake stays as an empty business until Claude removes it by hand; and a new business's object is created from a GitHub runner, so it is placed wherever Cloudflare chooses for that first request (the Paris finding in section 3 applies; not felt so far).

**Executed?** The guard and the workflow's structure are tested (88 checks, 14 breakages caught). The create route it calls has run on **real Cloudflare** for two businesses in every staging rehearsal. **The workflow has been run in production for its two safe paths (2026-10-17):** asked to create the live business `zululand-flooring-and-blinds` it read the real directory, saw 4 members and REFUSED (the create step was skipped, nothing written); asked to create a valid new business with a mistyped confirmation it REFUSED the same way. In both runs the record held no email. **The creating path has now run once in production (2026-10-17): it created the test business `tender-hub` ("Tender Hub", owner `t***@gmail.com`, Pierre's own second account).** Every step passed; the guard approved; the create answered 200 (`created`, `ownerInDirectory`, `ownerMembershipStatus` 200); the post-checks passed (in the directory, active, standard plan, the owner a member, its own object answering as itself); an independent check afterwards showed the live business still at 4 members and Tender Hub at 1. **`tender-hub` is a TEST business and stays in production until it is removed by hand** (there is no workflow to delete one).

### Checking whether something appears in a run's logs

`Log leak check` (GitHub, Actions, Run workflow): give it a run id (the number at the end of a run's URL) and a **placeholder** string; it downloads that run's logs **from inside GitHub** (this environment cannot) and records how many times the string appears, with control counts (so zero means "read the logs and it is not there", not "read nothing"). Counts only, in `ops/log-leak-check-last.json`. The needle is an input of that workflow, so it is visible in that run: use only a made-up address, for example `canary-123@example.com`, and test a new workflow by running it with that canary first.

## 15. Bringing a trial back (convert to a paid plan, or extend)

When a customer's 14-day trial ends, the owner can no longer sign in (they see "please contact us"). To answer them: GitHub, Actions, **"Production trial"**, Run workflow. Boxes: the **business id** (find it in `GET /debug/directory`: it is the name's slug plus six characters), the **action** (`extend` or `convert`), **days** (extend: 1 to 90) or **plan** (convert: for example `standard`), and the **business id again** in `confirm`.

- **extend** gives the trial N more days, counted from the LATER of now and its current end, so an ENDED trial comes back to life for exactly N days from today, and one still running gets N added. It stays on the trial plan.
- **convert** moves the business to the plan it pays for and clears the trial, so the owner signs in as a normal member (a normal 30-day session, the plan's limits).

It first reads the directory and the plans; a tested guard then **refuses**, before any write and with the run going red: a bad id, a mistyped confirmation, a business that does not exist, is not active (pending or suspended) or is **not on a trial** (an operator's business, or one already converted), a plan that does not exist or is `trial` itself, or days outside 1 to 90. If allowed it makes ONE attempt, then checks (a convert shows the plan and a cleared trial; an extend shows a later end by at least the days asked) and the run goes red if not. Only ids, plan names and numbers pass through: no personal data. After it, **ask the owner to sign in again** (their old session ended with the trial). Nothing is ever deleted.

**Executed:** the route on the REAL staging database in the rehearsal (refused without the confirmation key; extend moved the end by exactly 7 days; convert cleared it and set the plan; a repeat convert 409; an unknown action 400), and in the tests (including an ENDED trial brought back by extend and by convert). **Executed in production (2026-10-17):** the first real signup's test business had its trial extended by ONE day through the workflow: every step passed, the route answered 200, and the directory showed the end date move from 2026-10-31 18:49:18 to 2026-11-01 18:49:18 with the business still on the trial plan. **Not executed in production:** convert, and bringing back a trial that has actually ENDED (proven in tests and on the real staging database, not on a real ended trial).

## 18. Owners managing their own team (server done, no app screen yet)

**What an owner can do** (routes inside each business, owner-only; there is **no screen for it in the app yet**, so today nothing can call them but a future Team screen): `GET /team` lists the team (email, role, status, who added them, when) and the roles that may be given; `POST /team` `{email, role}` adds a person; `PATCH /team/:id` `{role}` changes a role; `POST /team/:id/deactivate` and `/reactivate`. The roles an owner may give today are **owner (a co-owner), accountant and installer**, with **no cap on the team size**. **Sales and admin were added 2026-10-18** (see the roles paragraph below). **How adding works.** The person signs in with that Google account and lands in the business; nothing is emailed (the app is to offer a share-sheet text). The directory and the business cannot share a transaction, so the order is: check, write the membership, write the directory entry; **adding the same person again finishes a half-done add** (the answer is a success with `healed: true`), so a failure part way never leaves a stuck state. **An address that already belongs to another business is refused with a message that does not say which** (one email, one business).

**Rules that keep a business from losing its owner or being taken over:** an owner is **never changed, deactivated or reactivated through the app** (only the operator can, with the workflows or by hand), nobody can change or deactivate themselves, and so a co-owner can never lock the first owner out. **Deactivating takes effect at once** (proved on the real object: the member's very next request is refused), but the person's address STAYS bound to this business in the directory (so they cannot start or join another business until the operator releases it; there is no release tool yet).

Mitigations today: an installer or accountant sees far less than an owner, deactivation is immediate, and the list shows exactly who is on the team and who added them. **A "joined / last signed in" stamp and an invite-and-accept step would close most of it; neither is built.**

### The empty-business handover, 2026-10-18 (`ee69977`)

**The problem.** An employee who signed up for their own trial by mistake has an address bound to that empty business, so adding them to their employer's business was refused ("belongs to another business"), and signing in took them straight to their own empty business: they never saw an invitation.

**What happens now.** The owner INVITES them (a direct add of such an address is still refused, now pointing at inviting instead). When that employee signs in with Google in a browser, and ONLY if their own business is **self-started, still on its trial, has exactly one member (them), and is verifiably EMPTY**, and they have a pending invitation to another business, the sign-in page ASKS them: **Join X (your empty business is closed; nothing is deleted)** or **Keep my own business**. Keep declines the invitation, so they are not asked again. Join closes the empty business (`status = closed`, `closed_into` = where they went: the only record of it), binds their address to the new business, creates the membership recording who invited them, and accepts the invitation. **Nobody can do this to them: it needs their tap, and the server re-checks everything when they tap** (a tampered form, a stale page, an invitation withdrawn meanwhile, or data added meanwhile all just sign them in to their own business with nothing closed). The order makes a failure part way recoverable (membership, close, move the address, accept): if it stops after the old business closed, the same person's ordinary Join finishes it, because **an address bound only to a CLOSED business conflicts with nothing and simply moves**. **Inviting is now neutral**: an address in another business is invited exactly like any other, and the owner learns nothing about it either way (refusing used to reveal that the person already has an account); for anyone who is not eligible the invitation just waits and expires.

**What "empty" means (emptiness.ts, asked of the real object by `GET /debug/emptiness`, a read-tier admin route).** Measured, not guessed: a business database has 42 tables and right after signup exactly TWO hold a row (memberships: the owner; business_profile: the name). Empty = every other table has no rows, the only member is the person asked about (an ACTIVE OWNER), and the profile holds nothing but a name. **Four tables are written by the PLATFORM for every real business and are ignored: `object_meta`, `schema_steps`, `admin_audit` (every privileged call is audited inside the object, and signup itself makes two) and `request_timings` (RECORD_TIMINGS is on in production).** Everything else counts, including any table a future feature adds, so the rule can only err on the safe side. **Two tests keep it honest: one puts a row in EVERY table and requires the answer to flip, and one FAILS if anyone adds a lazily-created table without classifying it as platform bookkeeping or owner data.**

**What it does NOT do.** It never merges data: a business with anything in it is never offered (those people use another Google account, or an operator sorts it out). It does not handle a person who is a MEMBER (not the owner) of a business, or an owner with several members.

### Quoting as its own capability (`can_make_quotes`, "Quotations"), 2026-10-18 (`19c73f9`)

**What it is.** A salesperson can now dictate a quotation, confirm it, edit it (`PATCH /quotations/:id`) and send its PDF link, WITHOUT being able to confirm payments, raise invoices, convert a quote into an invoice, or see any money. The quotation rules check the new capability ALONE, so the switch is real: an owner can take quoting away from an accountant without taking money away, give an installer ONLY quoting, or switch it off for sales, all from the existing permission screen (a new "Quotations" row).

**Nothing changes for anyone until an owner flips it.** Quotations FOLLOW "Money in and out" until set on their own (`INHERITED_FROM`, the precedent of 2026-10-04 for expense totals and supplier balances), so an accountant, admin or installer who had money could quote and still can, and one whose money was switched off still cannot. **Only sales is independent**: its default has quoting without money.

**Still money-only, deliberately:** `price_scope` (pricing a measured scope can produce an INVOICE), `convert_quote` (a quote into an invoice), invoices, payments, expenses, editing an invoice or a customer, and the finance list. So **sales quote with the plain "quote ..." phrasing; "price this scope" is still refused for them**, and **sales have no list of quotations**, only the link they get when they confirm one. Not exercised with a real dictated quote as a salesperson: the real rehearsal proves the gate and the switch, not a quote end to end.

**Two traps found before building, and why they are pinned.** (1) **"Follows its parent" strips a child its role has without the parent**: the old rule removed the child when the parent was absent, which would have silently removed quoting from sales; and the permission screen's "is this the default?" compared with the PARENT'S state, so switching quoting off for sales would have been treated as "back to default" and never stored. One shared helper, `followsParent(role, capability)`, now decides it for both the loader and the switch, and a role is independent ONLY when its static default has the child WITHOUT the parent (sales). My first version of the rule ("independent if the child is on by default") would have stopped the accountant's quoting from following money; the tests written first caught it. (2) **The "keep this sentence out of free-text notes" rule is DERIVED from the capability** (`intentKeepsOutOfNotes`: an intent whose creation needs money). ### Billing, slice 2: the payment flow, 2026-10-20 (LIVE: `25543cd`; INERT in production until PayFast is configured)

**What it does.** An owner (only: `can_manage_settings`, an owner-only capability) starts a checkout with `POST /billing/checkout {plan, interval, seats}`. That makes an ORDER in the shared layer (`billing_orders`) whose amount is fixed by OUR price table (the plan's price per seat times the seats; a Single user plan is always one seat; Team needs at least its minimum; a plan that is not public, has no price for that interval, or is the trial cannot be bought online; the request carries NO money field and the route never reads one). It answers with a `payUrl`: the public page `GET /billing/pay?order=<id>` (the unguessable order id is its only key), which is a signed PayFast subscription form that submits itself (monthly = recurs every month, annual = every year, from today, no end date). PayFast then reports the result to `POST /billing/payfast/notify`.

**The notification handler, in the order it decides.** (1) Payments not configured: 503. (2) A signature that does not verify (PHP-style `urlencode`, every posted field in the order sent, empty ones included, exactly as posted, constant-time compare): 400. (3) PayFast's own confirmation (`/eng/query/validate`; anything but exactly `VALID`, including an unreachable PayFast, is NOT confirmed): 400. Only then is anything read or written. Then: a payment already seen is a no-op (a unique PayFast payment id; one PayFast first reported FAILED may later complete, which is not a replay); the notification must name the order's own business; the amount must equal the order EXACTLY (a cent either way is a mismatch); a renewal must carry the subscription's own token; **a refused notification is recorded as `rejected`, changes nothing, and still answers 200 so PayFast stops retrying.** COMPLETE on a pending order puts the business on the plan with its seats, active, stores PayFast's subscription token, **ends its trial**, and sets the paid period (a month or a year from today; a shorter month clamps, 31 January plus a month is 28 February); COMPLETE on a completed order is a RENEWAL (the period runs from where it ended, not from today); FAILED marks the subscription `past_due` with a 7-day grace period and takes nothing away; CANCELLED marks it `cancelled` and keeps the period already paid. The ledger (`billing_payments`) holds amounts, ids, status and the subscription token, and **no names or email addresses**. The source address is recorded (`ip_ok`) but is ADVISORY: PayFast can change its ranges and a wrong list would silently reject real payments.

**Configuration.** `PAYFAST_MODE` is SANDBOX unless it is exactly `live`. Sandbox uses `PAYFAST_SANDBOX_MERCHANT_ID/KEY/PASSPHRASE`; live uses `PAYFAST_MERCHANT_ID/KEY/PASSPHRASE` and never borrows the sandbox merchant. `PAYFAST_SKIP_CONFIRM=1` (skip PayFast's confirmation, which cannot succeed for a made-up payment) works ONLY in sandbox and is ignored in live mode. **The production configuration file carries none of these (a test fails if it does); the secrets are to be set by the deploy from GitHub secrets, which has NOT been done**, so **production is inert**: a notification gets 503, a checkout says "Payments are not set up yet". The staging configuration (generated by `staging.yml`) has PayFast's own public sandbox merchant (10000100), an invented passphrase and the skip flag, for the rehearsal only.

My `CREATE TABLE IF NOT EXISTS payments` therefore silently did nothing, and my INSERT failed against the wrong table. Locally the shared layer held only directory tables. The ledger is now `billing_payments`; the billing tests run against a shared layer that also has the business tables; and **a test fails if any table the shared layer makes shares a name with a business table** (restoring the old name fails three checks). ### Access ends when paying stops, 2026-10-19 (LIVE: `254dcef`)

**The rule (`access.ts`, decided by DATE and only after PayFast has told us).** `past_due` (a payment failed): the business keeps working through its grace period (7 days, a date, **last day inclusive**) and is refused the day after. `cancelled`: it keeps working through the period it already paid for (last day inclusive) and is refused the day after. **An `active` subscription is never cut by a date** (renewals move it, and a lost notification must not lock out a paying customer). Any other state, a missing or unreadable date, a missing column and a database fault all mean NOT lapsed: **this check fails OPEN, by design** (authentication still fails closed). A fault therefore grants a business only what it had a moment earlier; the alternative is locking out someone who has paid because our directory hiccuped.

**Where it bites.** (1) **Sign-in** (`directory.ts`): a lapsed business is not found, and `findEndedAccessForEmail` says why, so the sign-in shows "Payment overdue", "Your subscription has ended" or the existing trial page (same contact line, nothing deleted). The lookup is **three-tiered** (trial + payment, trial only, nothing): the old fallback for a missing column dropped the trial rule, so adding billing columns carelessly would have silently stopped enforcing trials on older databases; a test pins that. (2) **Every request** (`authGate`, after the session and membership checks): a lapsed business gets `401 {code: "access_ended"}`, **the owner too** (no bypass), so a session issued weeks ago cannot outlive the lapse. It costs one directory read per business per minute (`ACCESS_CACHE_SECONDS`, default 60, memory kept per database binding; 0 turns it off, as staging does). A change is therefore seen within a minute. The original single-business mode (no business id, or no shared directory) makes no query at all. Public routes are not blocked, so the sign-in can say why. (3) **`/auth/me`** answers `{signedIn: false, code: "access_ended"}` for a lapsed business. Membership disabled or a role changed is unchanged and immediate (the gate re-reads the membership on every request).

**An operator can set a subscription state:** `POST /debug/directory/billing-state {business, billingStatus?, periodEnd?, graceUntil?}` (privileged). `billingStatus` is exactly `active`, `past_due` or `cancelled`; a date is a real calendar date `YYYY-MM-DD` or null to clear it; only the fields given change and nothing else (plan, seats, token) is touched. It exists to rehearse a lapse without waiting weeks, to correct a state, or to grant a free month (set `active` with a future `periodEnd`).

### A customer starts a payment on their own, 2026-10-19 (LIVE: `9395913`)

**The flow.** An owner reaches the **plans page** (`GET /billing/plans?t=<link>`), which lists our price table's PUBLIC plans (Single user, Team per seat with its minimum, monthly or annual; **Enterprise reads "talk to us"** with `SUPPORT_CONTACT` and is never a buy option, even if an operator gives it a price). The form (`POST /billing/start`) makes an order (billing.ts `createOrder`) and answers `303` to `/billing/pay?order=<id>`, the signed PayFast page. Every price on the page is read from the table (change a price and the page changes).

**How an owner gets the link.** (1) The sign-in's ended page for a **trial that ended** or a **cancelled** subscription shows **Choose a plan**, with a link made for the address Google just verified. (2) An owner signed in to the app can ask `POST /billing/plans-link` (owner-only, `can_manage_settings`; 401 with no session, 403 for every other role) and gets `{url}`. An **overdue payment gets no link**: it already has a subscription, and a second one would double-bill.

**The link.** `signBillingToken` / `readBillingToken` (auth.ts): bound to ONE address and ONE business, about **30 minutes**, signed over its own string (`billing.` + payload), so it can never pass as a session or a sign-up proof, and neither can pass as it. It proves only that the address was verified a moment ago.

**What is protected.** (1) **Only the OWNER**, and it is **re-checked at both steps** (the page and the form post), not just when the link was made, so a link made while someone was the owner stops working if they stop being it. (2) **The order is for the business and address in the SIGNED link; the form can only say plan, interval, seats and the link.** Extra fields (a business, an address, an amount) are ignored, and the amount always comes from our table. (3) A business that already has a subscription (active or past due) is told so (the page shows it; the form answers 409) and no order is made; a cancelled one may subscribe again. (4) **A cap of 20 open (pending) orders per business per day** (429 after that), so a leaked link or a script cannot open orders without limit; this also covers the operator route. (5) The page is `no-store`, escapes the business name, shows no payment secret, and when payments are not configured says so (503).

**Executed.** 60 plans checks, 23 breakages caught (three survivors were gaps in my tests, closed: a forged link with the wrong purpose, a priced non-public plan, a hardcoded Single user price; two others are redundant guards whose effect createOrder also enforces), both backends 7,220; the **REAL staging object 64 of 64** with raw answers kept: the owner gets a link and a second member 403; the page lists the plans from the real table; a tampered link is a 400; the form, with a made-up business and amount injected, makes a pending R399.00 Single user order for the signed link's business and answers `303` to the pay page, which is the signed sandbox form; an already-subscribed business is told so. ### PayFast's subscription API from the Worker, and updating a card, 2026-10-19 (LIVE: `31163d4`)

**The API client (`payfast-api.ts`, `billing.ts`).** Requests to `api.payfast.co.za` carry `merchant-id`, `version: v1`, a `timestamp` (South African time, UTC+2, `YYYY-MM-DDTHH:MM:SS+02:00`) and a `signature`: the **MD5 of those values plus the passphrase (left out when empty), keys in alphabetical order, values URL-encoded the PHP way**. The passphrase and merchant key are NEVER sent. Sandbox adds `?testing=true`; live does not. **This scheme was proved against PayFast's own sandbox:** its ping answered 200 with our signature and 401 "Merchant authorization failed" with a wrong one (so the merchant account also has the API enabled). On production, with the real sandbox merchant: ping ok; a read-only fetch returned the real Ballz subscription (status 1, R897.00, monthly, one cycle complete, next run 2026-11-19, matching our own record); **pause** moved it to status 2 and its next run a month later (2026-12-19); **unpause** returned it to status 1 and 2026-11-19. PayFast's status codes seen: **1 = active, 2 = paused**.

**Operator routes.** `GET /debug/directory/payfast-ping` and `GET /debug/directory/payfast-subscription?business=` are read-tier; `POST /debug/directory/payfast-subscription {business, action}` (`pause`, `unpause`, `cancel`, `fetch`) is **privileged** (it can stop a customer being billed). The `prod-billing-test.yml` workflow has them as `payfast-ping`, `payfast-fetch`, `payfast-pause`, `payfast-unpause`, `payfast-cancel` (the acting ones need the business id retyped). **Rules:** the subscription token is read from OUR record and put in the address only if it is exactly the shape of a PayFast subscription token (otherwise 409, nothing sent); it is **never returned** (an ALLOWLIST of facts comes back: status, amount, cycles, cycles_complete, frequency, run_date, billing_date, date_created, paused, cancelled; the buyer's details and anything PayFast adds later never get through, even if PayFast echoes them in an error); **an operator action never changes OUR record of the business** (our state moves only when PayFast's notification arrives, or an operator sets it with `billing-state`); every failure is a clean 502/503/409/404/400 that leaks nothing.

**Updating a card on a failed subscription.** PayFast's own SDK source gives the address: `https://www.payfast.co.za/eng/recurring/update/<subscription token>?return=<our page>`, and **PayFast's SDK refuses to build it in sandbox ("not available in Sandbox mode"), so this CANNOT be tested against the sandbox and is UNPROVEN until a real card is used live.** The "Payment overdue" sign-in page now offers **Update card** (a billing link made for that address and business) which goes to `GET /billing/update-card?t=`: it checks the OWNER again, requires the business to be `past_due`, requires the stored reference to be exactly a PayFast token, then answers `303` to PayFast's page (live) or "not available in test mode" (sandbox); `GET /billing/card-updated` is the thank-you page PayFast returns them to. The token appears nowhere except that one redirect.

**What PayFast does with a failing subscription (from PayFast's own help text, not tested by us).** It retries up to five times over five days and then LOCKS the subscription, which needs the merchant to reactivate it (PayFast's backend, or the API). Our 7-day grace period therefore ends about two days after the lock. **Reactivation after an owner updates their card is MANUAL for now:** an operator runs `payfast-unpause`; PayFast's retry then completes the payment and its notification puts our record back to active. Whether unpause re-arms a LOCKED (not merely paused) subscription cannot be tested in sandbox.

**Executed.** 37 API-client checks (16 breakages caught; one survivor was a real gap: PayFast's own error body echoing the token and email) and 28 card-update checks (13 breakages caught; two survivors were a bad mutation of mine and a missing check of where the cancelled page's button points), both backends 7,282; the REAL staging object **66 of 66** for the API client (PayFast's real answer from Cloudflare to staging's made-up passphrase was a clean 401, nothing leaked) and **67 of 67** for the card update (the refusals: a non-PayFast reference, an up-to-date business, a tampered link, and the thank-you page); production runs the commit.

### The reply envelope, Phase 1, 2026-10-19 (LIVE: `a064cbe`)

**What it is.** One new object, `experience`, added to the reply of the two app-facing routes (`POST /messages/text` and the voice-note route; NOT the debug transcription route). The contract is `ENVELOPE.md` at the repository root. **The principle (Pierre's): the intelligence thinks, the envelope projects, The Office becomes the experience.** It communicates what the reply has ALREADY established and recommends how a front end might present it. It is not an intent engine, not business logic and **not an authorization mechanism**: it grants nothing, decides nothing and executes nothing. It is additive and versioned (`version: 1`): every existing reply field keeps its name, value and meaning and `message` is always present, so today's app behaves exactly as before.

**The four parts, kept apart.** `established` (facts copied, validated and bounded from `pendingActions` as `{id, type}`, `pendingCandidates` as `{id, name}` and `pendingChanges` as `{field, label, displayValue}`, with `from` naming which reply fields were read); `recommendation` (`mode` is `clarify` when there are candidates to choose between, else `confirm` when there are held actions, else `speak`; `speak` repeats the message verbatim or is null); `unknown` (always `intent_class`, `room`, `workspace`, `evidence`, `certainty`, `refusal_reason`, plus `reply_field_malformed:<field>`, `reply_field_truncated:<field>`, `message_not_repeated` or `envelope_error` when they apply); `mustStillPass` (`confirmationRequired` is true exactly when something is held; execution happens ONLY through the existing confirm, reject and edit-field routes, which re-check authorization and validation on every call; the envelope carries no address, token, permission or capability).

**What Phase 1 deliberately does NOT do.** No intent classes (the current reply does not establish one). No rooms, workspaces, reports, evidence or certainty. **No `refuse` mode: a permission refusal reaches the app today only as words inside `message`; there is no structured signal, and guessing from text is not allowed (a test pins that refusal-sounding words stay a plain message).** No stakes grading (the type is passed through; the app already grades its confirm gesture from it).

**Safety properties (all pinned in `tools/experience.test.js`).** It is a pure function (`experience.ts` imports nothing, reads no database, checks no capability). Built from an allowlist of four reply fields only: nothing else (capabilities, e-mail, tokens, session, role) is ever copied. It never throws and never changes the reply: a malformed, partial or hostile reply (null, wrong types, junk items, circular objects, throwing getters, prototype-pollution keys) still yields a valid envelope or a minimal fallback naming `envelope_error`; the original reply is not mutated; a reply that already has an `experience` field is left untouched; anything that is not an object reply passes through as the same value. Bounded: 50 items per list, 200 characters per copied string, a message over 2,000 characters is not repeated (the `message` field is always the full text).

**How it was shown to be backward compatible.** The suite's golden recordings are real replies from the real handlers. The new field changed 19 of them (12 in `permissions.json`, 7 in `uploads.json`; the other twelve recordings did not change). I regenerated them with `GOLDEN_UPDATE=1`, then proved STRUCTURALLY, not by eye, that removing every `experience` block from the regenerated files gives back the old recordings exactly. The recorded modes are 16 `speak` and 3 `confirm` (the three genuine held-action replies).

**Executed.** 74 envelope checks, 28 breakages caught (see the lessons in DECISIONS.md), both backends 7,356; the REAL staging object 67 of 67 on the exact Worker code Pierre reviewed; deployed only after Pierre saw the test results and the proposed diff (7 files, 795 insertions; production code was one new 92-line pure module and three changed lines in `index.ts`).

**Not done (the rest of the backend wrap-up).** Phase 2: reports as data (profit and loss, aged debtors and creditors as JSON with a period and a comparison period; today they exist only as PDFs). Phase 3: the analysis layer, with contributors, evidence links and a `certainty` that says plainly whether a claim is a fact, a calculation or an inference. Phase 4: a history and audit record of heard, interpreted, proposed, executed and replied (today the server stores what was said, in `captures`, but not what The Office answered). ### The analysis layer (backend wrap-up point 2), 2026-10-19 (LIVE: `d1a7380`)

**What it answers.** `GET /reports/analysis?topic=expenses|profit&from=&to=` (optionally `compare_from`/`compare_to`) answers WHY a profit and loss figure changed. **A period is required and so is a comparison; the comparison defaults to the report's own previous period, which is the same LENGTH ending the day before** (October's 31 days compare with 31 August to 30 September, not the calendar month); `compare=none`, a missing topic, a topic in the wrong case or any malformed date is a 400 with a reason. It is stateless and read-only, so the open report is never touched, and it is authorised by exactly the capability that guards the profit and loss (`can_know_profit`): the route policy shows it behaving identically to `/reports/profit-and-loss` for every role.

**The rules (pinned in `tools/analysis.test.js`).** (1) **Every number comes from the report** (`profitAndLossData`); the module adds only differences, shares and sums of those figures. (2) **A finding is `fact` (read from a record) or `calculated` (arithmetic on report figures); none is ever a cause**: no finding says "because", "due to" or "as a result", and none is marked inferred. (3) **What it cannot know is listed, not guessed:** `notEstablished` always contains `cause_of_the_change`, `recurring_or_one_off` and `business_date` (periods are by the date a record was ENTERED), plus `supplier` for expenses (**expense records carry no supplier**, only an amount, a free-text description, a category, a date and an optional customer, so no supplier is ever named) and `cash_received` for profit (revenue is accrual). (4) **Evidence is read through the report's own date filter** (`getExpenseEvidence`, `getInvoiceEvidence` in finance.ts) so a record the report counts in a period is a record listed for it, border days and time zone included (a record stored at 22:30 UTC on 30 September is shown on 1 October), and **every evidence set carries `reconciled`** (does it add up to the report's own figure) and `truncated`; a finding says so if it does not reconcile.

**Shape.** `summary` (the metric, current, previous, change, direction, and for profit `reconciles`: the three contributors' effects add up exactly to the change in net profit, or the analysis says the report's own figures do not add up); `contributors` (expenses: categories ranked drivers first then offsets, each with its change, its `shareOfChange` (which can exceed 100% or be negative when others offset it), `part` (`driver`, `offset` or `none`), `flags` (`new_in_period`, `absent_in_period`) and, for the top three drivers only, up to five evidence records from the CURRENT period when expenses rose or the COMPARISON period when they fell; profit: revenue, cost of sales and operating expenses with `effectOnProfit` (a cost rise is a NEGATIVE effect), revenue's evidence being invoices, and a `drillDown: {topic: "expenses"}` pointer on the cost lines); `findings`; `notEstablished`; `limits`. **The field is `part`, not `role`, on purpose: `role` means a permission role in this codebase and the role-name audit rightly flags it.**

**Executed.** 51 checks (a real-database test proves the analysis totals equal the report's and the evidence reconciles across a time-zone border and for the uncategorised "other" category), 25 breakages caught (the survivors were real gaps: nothing asserted the evidence for the uncategorised category, and a displayed date being the UTC day), both backends 7,491; the REAL staging object **71 of 71** with the raw answers kept (owner 200 for both topics, a second member 403, a stranger 401, malformed requests 400 with their reason). **The staging business has no expense data, so the real-object run proves the route, the authorization and the report's real-database path, not the evidence queries on real rows; those are proven locally.**

### The history and audit record (backend wrap-up point 3), 2026-10-19 (LIVE: `02987c2`)

**The doctrine it serves.** Conversation history is a RECORD, not the main experience, and a transcript alone does not establish what happened: a spoken request, an interpreted intent, a proposed action, a decision on it, an executed record and the reply are different things. So they are kept as different things.

**What is recorded (`history.ts`, tables created lazily in each business database).** (1) `interaction_log`: one row per message turn, written AFTER the reply is built at the two message routes (text and voice note): `actor_email` (tidied), `source`, `capture_id` (the stored capture of what was heard), `interpreted` (the extraction as JSON, cut at 2,000 characters and marked truncated), `proposed` (the held actions, `[{id, type}]`) and `mode` (the envelope's recommendation), both taken from the reply envelope's OWN function so there is one derivation, and `replied` (cut at 4,000). **The heard text is NOT copied: it stays in `captures.raw_text` and is read from there.** (2) `action_events`: a decision on a held action (`confirmed`, `rejected`, `edited` for POSTs to `/actions/<id>/confirm`, `/reject`, `/edit-field`) with `actor_email` and `outcome` (`done`, or `refused:<status>`, so refused attempts are recorded too), written at the single place the request handler is called, **from the response status alone: the body is never read**. Only an allowlist of the reply is stored: no capabilities, tokens or addresses beyond the actor. Both tables are append-only (nothing in the module deletes, drops or alters) and use `created_at`, which the golden harness masks.

**Recording can never change a reply.** Every write is swallowed: a database that is down, a malformed reply, a circular object or a throwing getter makes recording return false and never throws. The capture id reaches the recorder through an OPTIONAL callback on `processTranscript`, so **the reply object gains no field** and no recorded reply changed. The debug transcription route is not recorded.

**Reading: `GET /history?who=me|all&limit=1..100&before=<id>`.** Open to every member (like the message routes), but **a member only ever receives their OWN turns** (matched on address, regardless of case); `who=all` needs `can_manage_settings`, an owner-only capability (403 otherwise). Each item keeps **`recorded` (the heard text, from the capture) visibly apart from `generated` (interpretation, reply, mode)**, then `proposed` (each held action with its CURRENT status), `decisions` (what was done with them: in a member's own view `by` is "you" or "another member" and never another person's address; in the owner's view it is the address) and **`recordsWritten`: the business records created from that utterance, traced at read time through the `capture_id` that 18 tables already carry** (nothing is guessed, and nothing is instrumented inside the pipeline). If the capture was deleted, `heard` is null and the rest remains. Reading is read-only, paged by a cursor with no repeats, and tolerant of tables an older database lacks.

**Classification.** The two tables count as the owner's ACTIVITY for the empty-business rule (a business that has had a conversation is not empty); they are not platform bookkeeping.

**Executed.** 56 checks, 22 breakages caught, both backends 7,550; **18 golden recordings gained a history write** (12 in `permissions.json`, 6 in `uploads.json`) and removing them gives back the old recordings exactly; the REAL staging object **74 of 74**, including a genuine message through the live pipeline read back from `/history`, a second member seeing none of it, a non-owner refused `who=all`, and a decision on an unknown action refused cleanly (404) with the history still readable afterwards.

**Not done.** A retention or purge policy: the record is append-only and nothing expires it, which matters for POPIA (what is kept, for how long, and who may erase it) and needs Pierre's and a qualified person's decision; an owner-facing way to erase a person's history on request; recording the DIRECT executions made inside the pipeline as events (today "executed" is traced from the records that carry the capture id, which is true but only for the 18 traced tables); the edit-field change itself (which field, to what) is not recorded because the request body is deliberately never read; workspace context (point 4).

### Workspace context (backend wrap-up point 4), 2026-10-19 (merged `5b50771`; the contract for the front end is `CONTEXT.md`)

**What it is.** The app MAY tell The Office what the user is looking at, so a follow-up such as "compare that to August" can later be understood. **In this phase the context is accepted, validated and RECORDED with the turn, but it is NOT used to interpret speech: the AI pipeline has no notion of reports or periods (it uses conversation history only to resolve WHO a follow-up refers to), so no consumer exists, and wiring a hint into prompts today would be speculative and would widen a client-supplied path into a prompt.** Sending it therefore changes no reply. The first consumer will be the intelligence layer; context is already flowing when it exists.

**An untrusted hint, never a permission (`context.ts`, a pure function).** Validated against allowlists: `version` exactly 1; `room` a lower-case slug (shape only: the app owns its room names); `report` one of `profit_and_loss`, `aged_debtors`, `aged_creditors` (the reports the server really has); `period` and `compare` exactly `from` and `to`, real dates, `from` not after `to`, at most 3,660 days, a `compare` only beside a valid `period`; `filters` at most 10 entries with slug keys and short plain-string, finite-number or boolean values; `sort` a slug; `selection` at most 5 entries of exactly `{type: slug, id: positive whole number}`; the whole context under 4,000 characters. **An unlisted field (role, capabilities, token, address, anything claiming authority) is DROPPED and its NAME reported as `unknown:<name>`, never kept; a rejected VALUE is never echoed; a bad field never costs the message (valid parts are kept, dropped parts are named); the validator never throws.** The context is never handed to `processTranscript` or to anything that decides access: capabilities are resolved from the session exactly as before.

**How it travels.** Text: `"context": {...}` in the body of `POST /messages/text`. Voice note: the body is the audio, so the same JSON as base64url in the `X-Office-Context` header (up to 5,000 characters; a bad header is ignored and costs nothing; `X-Office-Context` is on the CORS allow-list for a browser client). **Dry run while the front end is built: `POST /context/check {context}`** answers `{context, rejected, used: false, note}` (what WOULD be kept and dropped), open to every signed-in member, reading and changing nothing.

**What is recorded.** `interaction_log.viewing` (a new nullable column; **a table created before it existed is upgraded the first time it is written, and an old table is still readable**): what the APP said was on screen, re-validated at the recorder (so nothing unvalidated can be stored), null when there is nothing to record (an empty or fully rejected context is recorded as null, not as "{}"). `GET /history` shows it as `viewing`, beside, not inside, what was heard and what was generated.

**Executed.** 87 checks, 31 breakages caught (the survivors were a mutation too weak to take effect, an untested empty-context case and a suite I had not run it against; all redone), both backends 7,639; **18 golden recorded history rows gained a null `viewing` key and removing it gives back the current recordings exactly**; the REAL staging object **76 of 76**, including a message sent with a deliberately hostile context (a fake `role: owner`, capabilities, a token, a bad report) whose history shows only the validated parts, and the dry run for a member, a malformed request and a stranger.

**Not done.** Using the context to interpret speech (needs the intelligence layer); the voice header is not exercised by the real rehearsal; **the upgrade of a history table created before `viewing` existed is proven locally but not on a real object (production's tables are in that old shape and upgrade on their first write; the worst case is that new turns are not recorded until fixed, replies are unaffected because recording is swallowed, and reading tolerates the missing column)**; a retention and erase policy for the history (POPIA).

### Front end, slice 1: the app handles a lapsed business, and the app has tests, 2026-10-19 (MERGED to main; NOT yet verified on a device)

**The audit that chose it.** Against the design doctrine, the Flutter app (one 8,785-line `main.dart`) ALREADY has the void (`VoidLake`), the orb (`FilamentOrb`), an ember system, fifteen rooms, a drawer, a transient response overlay (`_ActiveResponse`) and the hold-to-confirm gesture for actions. The 401 was the first gap that hurts today: the backend now refuses a lapsed business on every request, and the app would show broken screens.

**What it does (`app/lib/access_guard.dart`, wired in `main.dart`).** ONE shared client (`AccessAwareClient`) is installed with `http.runWithClient`, so none of the 40 top-level `http` calls or the 4 multipart uploads changed. It reads ONLY a 401 response: a body that is a JSON object whose `code` is exactly `access_ended` raises a one-shot signal (`AccessSignal`); every response, that 401 included, is handed back to the caller with the same status, body and headers; every other response streams through untouched. The signal clears the stored `session_token` (a failure to do so never stops it), and `AccessGate`, which now wraps `OfficeHome` as the `home`, closes anything open on top (`popUntil` first route, through a root navigator key) and replaces the whole home with a calm "Your subscription has ended" screen (a live region for screen readers, a single "Sign in" button). "Sign in" clears the signal, so the home is built afresh, finds no session and shows the ordinary sign-in, where the server's own page says why. Two traps are designed around and tested: package:http makes and CLOSES a client for every top-level call, so the wrapper shares one inner client and its `close()` does nothing; and a dialog open at the moment of the 401 would otherwise stay on top of the new screen.

**CI is now the app's test runner and its record (`.github/workflows/app-compile-check.yml`).** It runs `flutter test` and commits `ops/app-compile-last.json` (the commit, each step's outcome, the analyzer's error lines, the failing test lines and the test tail) so a result can be READ rather than inferred from a green or red mark. It runs on every branch except `main`. It also now removes the stock counter test that `flutter create` generates during the web bootstrap (it refers to a `MyApp` class this app does not have, so it could never load and made every test run fail).
