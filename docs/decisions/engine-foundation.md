# DECISIONS: engine-foundation

Branch `engine-phase1` (pushed to GitHub; not merged, not deployed). Decided with Pierre 2026-11-01/02 after the architecture assessment (rebuild the engine core on the retained platform substrate, in this repository). ## Engine foundation: the facts are recorded once and corrected, never edited (2026-11-02)

**Decided.** The engine's records are FACTS (`eng_event`, `eng_party`, `eng_party_role`, `eng_document`, `eng_document_line`, `eng_document_number`, `eng_money_movement`, `eng_allocation`, `eng_reversal`, `eng_interpretation`) and WORKING STATE (`eng_config`, `eng_draft`, `eng_observation`), 13 tables in migration `0004_engine_foundation.sql`. A fact is recorded once and never edited. A mistake is corrected by a REVERSAL (`eng_reversal`, exactly one target, once, with a reason) and, if need be, a replacement fact recorded in the same transaction. Reversed facts are simply not effective: `ledger.ts` derives every position (what a document owes, what a payment has left, what a customer owes) in ONE place from effective facts, and what hangs off a reversed fact is not effective either. A fact with live dependents cannot be reversed alone; nothing is reversed twice.

**Money and quantities are integers**: minor units, thousandths, basis points. No floating point anywhere. A product that could pass 2^53 is computed with BigInt, rounded half up per line, and refused (`amount_out_of_range`) when it cannot be held exactly. SQLite coerces `'1000'` to 1000 and stores 1.5 in an INTEGER column, so the database enforces what it can (`typeof()` checks refuse floats and non-numbers) and the engine's own write path refuses text.

**No database triggers, and why.** The migration runner splits a step on `;` and `schema.test.js` refuses any step containing `DELETE`, so append-only triggers cannot be a migration without changing the runner, which has platform-wide blast radius. Restore also wipes every live table with `DELETE FROM`, so a delete-blocking trigger would have blocked recovery. Instead (CORRECTED 2026-11-02 after the read-only investigation; the first wording of this paragraph overstated the guarantee): the engine's write path (`facts.ts`) only inserts into fact tables, and a test scans `worker/src/engine` for any update, delete or replace of a fact; whether OTHER code writes these tables is now PINNED by a static test (Task 3, `tools/engine-ownership.test.js` rule R6: the ten fact tables are insert-only everywhere in the source, written only by `facts.ts` plus the single `operation.executed` insert in `capability-contract.ts`), which is a source-level tripwire and not a runtime or database guarantee, so "one write path" is a convention with two code scans, not a proven boundary. `verifyIntegrity` (read-only, `integrity.ts`) is PARTIAL detection after the fact, not prevention. The CURRENT, complete statement of what is checked, what is tested and what is not detected is the section "Engine integrity: the invariants, the event model, and what a clean result means" below (Task 2 extended the verifier after this paragraph was corrected). In short: it runs only when called (its only caller outside the tests is the admin status route, `engine/admin.ts`), and a clean result is not proof of authenticity. So the engine's immutability is enforced by convention in one write path plus code scans, and detected in part; it is not prevented by the database, and arbitrary changes are not guaranteed to be detected. The trade-off is real: the database itself cannot stop a raw `UPDATE`. Changing the runner to allow triggers is the alternative, and it is the owner's decision. Decision (2026-11-02, review): option C, strengthen detection and its tests first and evaluate triggers separately as an experiment; their behaviour on a real Durable Object, and with snapshot and restore, is UNKNOWN (triggers have only ever appeared in tests on Node's SQLite).

**Idempotency** is one `operation.executed` event per approved proposal (unique index), not one event per type, because one payment can settle two invoices. The facts a proposal records may be several; its execution is recorded once.

**What a document kind means is not decided by the engine.** Which kinds a customer owes for is configuration (`eng_config` `receivable_kinds`, default `invoice`; `payable_kinds`, default `supplier_invoice`).

**Evidence.** `tools/engine-schema.test.js` (59 checks, red 14 of 14 before the migration existed), `tools/engine-ledger.test.js` (66, red before the module existed; a failure injected at every write of issuing a document, of a payment that settles two invoices and of a correction leaves nothing behind and no gap in the numbering), and `tools/engine-breakage.js` (25 mutations of the engine's guarantees, all caught; the first run had one survivor, a derivation clause no test exercised, which a new test now catches).

## Engine and legacy coexist by mode, and every way in is classified (2026-11-02)

**Decided.** A business is EITHER an engine business or a legacy one, stored once (`eng_config` key `mode` = `"engine"`; absent means legacy). The two never write the same business's records: the legacy domain code writes the legacy tables, the engine writes the `eng_` tables, and the engine never reads or writes a legacy domain table. (Observed by code inspection on 2026-11-02: engine files touch no legacy domain table and import only `atomic`, `capability-contract` and `types`; legacy code names `eng_` only in `capability-contract.ts`. NO test pins either direction yet.) The protection is not one check at `/messages/text`; every entrance is inventoried and tested against the real request handler (`tools/engine-boundary.test.js`, 30 checks, red before the code):

- HTTP: every write route in `ROUTE_POLICY.md` (52) is classified in `worker/src/engine/boundary.ts` as a legacy business write (19), the shared held-action lifecycle (confirm, reject, edit-field), a platform route (always works), MCP, or public. A new write route that is unclassified FAILS the inventory test. In an engine business all 18 distinct legacy business-write routes are refused 409 `engine_mode` BEFORE they run and nothing is written; platform routes answer identically in both modes; in a legacy business `/engine/*` is refused 409 `not_engine_mode` and the legacy routes are reached exactly as before. A route the auth gate answers first (a signed-link upload) is covered by a direct test of the engine gate.
- Held actions: confirm, reject and edit-field refuse an action of the other kind BEFORE it is claimed; it stays pending.
- MCP: an engine business offers NO legacy tool, reads included (a legacy report over an engine business's empty legacy tables would say "owes nothing" and be wrong); a legacy business offers exactly what it did. Engine tools will be listed only in engine mode, so the pinned 14-tool list is unchanged. NOT done in phase 1: an engine MCP tool.
- Background work: the cron consolidation writes only `pending_memory_flush` and `memory_errors`; the object's alarm writes only its own bookkeeping. Checked by extracting each function body and comparing the tables it writes with an allow-list.

**Reused, not rebuilt:** the same Worker and Durable Object, sessions, memberships, `ROUTE_RULES`, the held-action lifecycle, backup and restore (it lists every table, so it covers the new ones). **Added:** the engine's own permission check, availability and validity checks at the door and again at confirm, and the mode gate, placed right after authentication.

**Evidence to expand beyond receivables** (recorded now so it is not invented later): the slice passes in CI on both backends, a staging rehearsal and a restore drill on the engine tables; the owner accepts the experience on a phone; one approved model-backed interpretation run; the procurement chain is built on the same foundations without changing any foundation table (phase 1 proves this on paper and in executable walk-throughs, below); and a parity decision (port, replace, drop) is made for each legacy capability.

## Engine operations: five conditions, one boundary, the record contract (2026-11-02)

**Decided.** An operation passes through five conditions, told apart, each failing with its own answer: UNDERSTOOD (`unknown_capability`), AVAILABLE to this business (`capability_unavailable`), PERMITTED for this member (`not_permitted`), VALID NOW (`invalid_payload`, `not_found`, `stale`, `over_allocated` and the other state codes), EXECUTED (authorised, atomic, once). Availability is business configuration (`eng_config` `available`), folded into the proof's contract without touching the lines its breakage script matches (all 14 of that script's mutations still caught). Permissions are the ENGINE's own vocabulary (`receivables.read`, `payment.record`, ...) behind an adapter (`permissions.ts`) from today's capability names; a legacy capability nobody has decided about grants nothing and FAILS a test until someone decides.

**The door** keeps what was said first, answers honestly, and for a request it cannot act on writes an OBSERVATION (a possible unmet need, never an invented operation). A held payment carries the EXACT allocations the approver will approve (oldest-first is resolved at the door, not left to execution) and the VERSION of the account it was based on. At confirm, inside the transaction, `check` runs again: an approval is only ever for what it showed (`stale`). A replayed approval is refused twice over: stale, and, for one written without a version stamp, by the one-execution rule, which rolls the whole attempt back.

**The record contract** (`records.ts`): every consumer reads the same view of a record: identity, VERSION (the latest event touching it or anything hanging off it), fields (each derived figure says which derivation produced it), collections, relations to follow, the actions THIS member may take now with whether each is valid, history. A record the member may not see answers exactly as one that does not exist (same status, same body). Through the route and through the function the answer is byte-identical for the same facts. Exports (PDF, share link) are listed as not yet available: they are phase 3.

**Drafts** (`drafts.ts`): the one mutable thing; saved incomplete, validated on every save, totals recalculated by the engine, versioned against overwriting; issuing validates strictly, creates and numbers the immutable document and closes the draft in one transaction.

**Evidence.** `tools/engine-operations.test.js` (61 checks, red before the code): the adapter's completeness, drafts, both reads, the door, the confirm through the real route, the same operation through two entrances. Atomicity of the confirm is proven on the real confirm function with real transactions (every backend) and through the route on the Durable Object step.

## Engine migration 0004: recovery plan, and what is NOT proven (2026-11-02)

**The migration is additive** (`CREATE TABLE/INDEX IF NOT EXISTS` only, no trigger, nothing with the forbidden words), so it is safe to roll code back while objects are already on the new step: the tables stay, inert. It applies automatically to every business's object like any step; a business that never uses the engine keeps the tables empty. In phase 1 it has been applied ONLY to test databases.

**What restore does with it (read from `backup.ts`, then tested):** restore wipes every LIVE table (not only the snapshot's) and refills the snapshot's tables parents-first. So restoring a snapshot taken BEFORE the migration on a business that has the engine tables and data restores the legacy tables exactly and leaves the engine tables empty and present; restoring a snapshot taken AFTER rolls them forward exactly. `tools/engine-restore.test.js` (20 checks) proves, on the harness: engine tables back exactly (rows, ids, numbering, derivations, foreign keys), legacy tables untouched, the business still an engine business after the round trip, and the pre-migration rollback and roll-forward both exact.

**Rehearsal on the real platform (NOT done; needs the owner's approval; it is what the recovery gate still lacks):** (1) take snapshot A on a staging business; (2) deploy the branch (the migration applies); (3) create engine data; (4) take snapshot B; (5) restore A and compare the legacy tables' fingerprint with the original and check the engine tables are empty; (6) restore B and check the engine tables are identical and `verifyIntegrity` is clean; (7) record the run. The harness cannot measure Cloudflare's memory limit, which is what failed on 2026-10-28; the restore code is schema-agnostic but the margin with engine data at size is unmeasured.

**Not proven, stated plainly:** the recovery gate stays OPEN (three synthetic drills were met earlier; the rehearsed rollback and the owner's acceptance remain). Nothing here is deployed.

**Known discrepancy, left deliberately.** The comment at line 4 of `worker/migrations/0004_engine_foundation.sql` says an integrity verifier "re-derives every invariant". The verified implementation does less: see the corrected paragraph under the first section. The migration is already applied on staging, so its file is NOT edited; this record is where the discrepancy is kept.

## Engine schema fit: later domains and the stop rule (2026-11-02)

**Decided.** The foundation tables must carry the other domains WITHOUT CHANGING. `tools/engine-fit.test.js` (23 checks) walks the representative relationships, with the later domains' tables written inside the test as a later migration would write them (new tables pointing at the foundation):

- Sales: a quotation revised (a `revises` link; which is current is derived) and accepted (an event), an order, delivery in two stages, partial invoicing, part-payment, a credit note applied as a NON-CASH movement allocated to the invoice with a link to the note, and a payment recorded against the wrong customer corrected by reversal and replacement. A quotation is not a debt (configuration, not a rule about names).
- Purchasing: PO, two receipts that over-deliver (the surplus is derived and decided by an event), a supplier invoice dearer by 50 cents a unit (the variance is derived from linked lines), and money out settling it through the SAME allocation mechanism as money in.
- Jobs: profitability derived from what is ATTRIBUTED to a job (revenue, supplier cost, labour) and traceable to documents; visits, assignment, completion with evidence (a captured photo); a job's completion precondition derived from its visits.
- Capture to outcome: one query walks what was said, how it was understood, the proposal, its confirmation, the execution and who approved it.

**THE STOP RULE:** if any lifecycle needs a column on a foundation table, the suite fails and the foundation is corrected before anything is built on it, not defended because it exists. After all of the above not one foundation table changed shape; a control proves the detector can fail.

**Known limits, not hidden:** these are derivations written for the test, not capabilities; stock valuation, tax beyond a per-line rate, retention release, foreign exchange and capacity are rules outside the foundation and untouched; supplier credits would follow the sales-credit pattern and are not walked.

## Engine migration rehearsal on real Cloudflare: what it does, and what it needs (2026-11-02)

**Decided (approved by Pierre 2026-11-02).** The harness proves the recovery logic; only a real Durable Object proves the platform, so the existing staging rehearsal (`staging.yml`, `mode: rehearsal`, staging's Worker and objects only, never production) is extended, not replaced. Part 1 runs BEFORE the deploy, while the previous code is still live: it snapshots `staging-two`. The deploy then applies the real migration 0004 to the real object when it wakes (alongside the workflow's own throwaway probe migration, numbered 1000 and up so the two cannot collide). Part 2 runs at the end: (1) the migration reached the object and the 13 engine tables are there and empty; (2) the object is put into engine mode with a known sample and snapshotted again; (3) ROLLBACK: the pre-migration snapshot is restored; the legacy tables must come back exactly (per-table counts against the manifest recorded before the deploy), the engine tables must be empty and still present; (4) the restore also brought back the record of applied schema steps, so the object believes 0004 is pending: `POST /admin/schema/retry` must re-apply it as a no-op and leave nothing pending; (5) ROLL FORWARD: the snapshot with engine data is restored; the engine must be back EXACTLY (per-table counts and content hashes, availability, integrity). A verdict of 14 booleans is recorded in `ops/staging-last-run.json` as `engine_migration_rehearsal`, and the step fails visibly if any is false.

**What it adds to the Worker, narrowly (`worker/src/engine/admin.ts`).** `GET /admin/engine/status` (tier read): mode, availability, a row count and a content hash per engine table, and the integrity verdict. `POST /admin/engine/provision-sample` (tier PRIVILEGED: both admin secrets): puts an engine-empty business into engine mode with the known sample. It exists ONLY where `ENGINE_REHEARSAL=1` (a variable `staging.yml` writes into staging's Worker configuration and production does not have), needs the business id as confirmation, and refuses a business that already has engine data, so it can neither top up nor overwrite. Tests: `tools/engine-admin.test.js` (16 checks; the hashes are proven stable, sensitive to damage, and identical after a restore round trip) and five deliberate-breakage mutations in `tools/engine-breakage.js`. The admin-gate test pins both routes: 175 admin routes, and the privileged list is now exactly 41.

**What it will and will not prove.** It proves the migration applies on a real object, the pre-migration rollback and roll-forward on a real object, and that the schema step is re-applied cleanly after a rollback restore. It does NOT measure Cloudflare's memory margin with engine data at size (the sample is a few dozen rows; the 2026-10-28 failure was about size), and it does not by itself close the recovery gate: that still needs the owner's acceptance of the result. Nothing runs against production.

## Restore verification no longer cries wolf after a column-adding migration (2026-11-02)

**Found** by the staging rehearsal (run 41445346938): 12 of 13 checks held on a real Durable Object, and the rollback restore reported `table customers: same row count (101) but the contents differ` and `ok: false` for a restore that had worked. **Cause (read in `migration.ts`, then reproduced locally with a control):** the restore verified by hashing every LIVE column of each row; the snapshot's hash was taken before the rehearsal's throwaway probe migration added a column to `customers`, so after the restore the live rows carried an extra column and the hashes differed although the counts, and the data in every snapshot column, were identical. It is not specific to the probe: the migration rules allow `ALTER TABLE ... ADD COLUMN`, so after any such migration a restore of an older snapshot would have reported a false failure for that table, and an operator could not tell the benign case from real damage. Migration 0004 adds only tables, which is why every other check held.

**Decided.** The restore now verifies by hashing the live rows over the SNAPSHOT'S columns (`fingerprint(env, only)` in `migration.ts`, the columns taken from the snapshot's own manifest in `backup.ts`). A column added since is not a difference; a changed value in a snapshot column, or a snapshot column that has gone missing, still is. Whole-table comparison for a migration between two businesses is unchanged. Tests: `tools/restore-added-column.test.js` (10 checks, red first: the false failure reproduced, and sensitivity proven so the fix cannot quietly blind the check) and two deliberate-breakage mutations in `tools/engine-breakage.js` (revert the fix; blind the check).

**Not claimed, and accepted as it stands (Pierre, 2026-11-02).** This is proven on the harness with a control; it has NOT been re-proven on a real object, and the staging rehearsal cannot simply be re-run as written: the first run left `staging-two` in engine mode with 30 engine rows, so a second run would no longer start from a pre-migration object (`provision-sample` refuses it by design). The offered way to re-prove it was to make the rehearsal repeatable by restoring the first run's pre-migration snapshot (`20261102T123131Z`, kept among a business's 14); Pierre chose not to spend a further staging run on it for now. Until it is re-proven the honest statement is: the rollback to a truly pre-migration snapshot was exercised once on a real Durable Object, with every check holding except the one this section fixes.

**Recovery-hardening gap found afterwards (read-only investigation, 2026-11-02; not a defect in the fingerprint fix): FIXED on the branch by Task 4 item 1, see the section "Recovery hardening: the snapshot manifest is validated before anything acts on it" below.** The original finding, kept for the record: `readManifest` parsed the manifest and cast it, checking only `complete`, `business` and `name`; the manifest has no checksum of its own (each part is checksummed against numbers stored IN it); and the verification read `t.columns` after the replacement transaction had committed. Nothing here closes the recovery gate.

## Engine integrity: the invariants, the event model, and what a clean result means (2026-11-02)

**Three things, kept apart.** ENFORCEMENT is what the engine's write paths and the database actually prevent. DETECTION is what the verifier can identify after a change. EVIDENCE is what the tests and CI establish. A guarantee is claimed only where the evidence for it is named. Task 2 strengthened DETECTION; it changed no enforcement, no schema, no trigger and no scheduling.

### What a clean result means (read this first)
**A clean result means: no violation was found among the invariants this verifier checks.** It does NOT mean the data is authentic, unaltered or complete. Neither a fact nor its event is independently protected (there is no hash chain and no external copy), so these are NOT detected, and `tools/engine-integrity.test.js` PINS each as executable evidence: (1) a COORDINATED edit of a fact and its event; (2) the deletion of a fact AND its event; (3) a swap of two documents' numbers (the number is not in the event and a swap leaves no gap); (4) an edit of a document's terms (not recorded in the event). Closing (1) and (2) needs an event hash chain or an external record, which is a schema change with backup, restore and rollback implications and is NOT part of this task; closing (3) and (4) needs the write path to record more in the event, which changes what NEW documents record. Each is a separate decision.

### The event model (`EVENT_MODEL` in `integrity.ts`, derived from what `facts.ts` and `capability-contract.ts` write)
Eight event types each create EXACTLY ONE fact row, carried by that row's `event_id`: `party.created` (one `eng_party`, plus one `eng_party_role` per role in its payload), `document.issued` (one `eng_document`), `payment.recorded` (one payment, direction in), `payment.made` (one payment, direction out), `payment.allocated` (one allocation), `payment.reversed`, `payment.allocation_reversed` and `document.reversed` (one `eng_reversal` whose target is a payment, an allocation or a document respectively). `operation.executed` creates NO fact. **Any other event type is NOT MODELLED and is a WARNING, never a violation:** it does not flip `ok` (it may come from newer code that was rolled back, or from a type nobody has modelled yet). **An event whose payload is not a JSON object is a violation** (`event_payload_malformed`). Both directions are checked, and a test fails if the engine writes an event type that is not in the model.

### The invariants, the code each is reported under, and the test
| Code | Invariant | Test (`engine-integrity.test.js` unless stated) |
|---|---|---|
| `event_without_fact` | a modelled fact-creating event has its fact (a deleted payment, allocation, reversal, party or document is found) | five deletion cases |
| `event_multiple_facts` | exactly one fact per event | two payments on one event |
| `fact_wrong_event` | a fact's event exists and is the kind that creates it; a payment's direction matches its event | wrong kind, nonexistent event, a role on another party's event, a flipped direction, an `operation.executed` event with a fact |
| `fact_changed` | a party (kind, name, role set), payment, allocation or document (header, reference, lines, recomputed totals) equals the snapshot its event recorded | party rename and kind, deleted roles, allocation edit, document header, line and reference, payment edit |
| `reversal_mismatch` | a reversal row's target, reason and replacement equal what its event recorded | reason edit, re-pointed target |
| `over_allocated` | no payment or document has more allocated than it holds or owes | a document case and a payment case, each isolated |
| `allocation_on_reversed` | no allocation is counted on a reversed payment or document | `engine-ledger.test.js` |
| `number_gap` | numbering runs 1..n; every document has a number | a hole, and a missing number |
| `orphan` | foreign keys point at something | an allocation to a nonexistent document |
| `event_payload_malformed` | every event payload is a JSON object | a fact event and a non-fact event |
Not checked at all: `eng_interpretation` and the working-state tables (`eng_config`, `eng_draft`, `eng_observation`). The previously untested comparisons (allocation, document) and the document over-allocation and orphan paths now each have an isolated test that asserts the specific code, and `engine-ledger.test.js` and `engine-restore.test.js` now assert codes where they used to assert only "not ok". Every new check has a deliberate-breakage mutation in `tools/engine-breakage.js` (51 in all, every one caught).

### When it runs, and what a failure does
It runs ONLY when called: today the admin status route (`engine/admin.ts`) and the tests. **Decision (2026-11-02): record only; automated scheduling is left to a separate decision**, because an hourly stored result raises separate questions (cost: the verifier is O(N) in memory and queries and unmeasured at size; staleness; failure handling; behaviour when a check is incomplete). **Failure policy: report-only.** A failed check reports specific findings. It blocks no write, repairs no record and triggers no restore. Report-only does not mean ignoring a serious finding: it keeps detection separate from remediation until the cost and consequences of enforcement are established.

### Seeded-business verification (local, 2026-11-02)
The stricter verifier was run against the provisioning route's sample (the same code that built `staging-two`'s engine data on the real platform), the raw-SQL seeded business the route tests use, and an empty engine: all reported no problems and no warnings, so there were no findings to interpret. **Not done:** the real `staging-two` object itself has not been verified; that needs the admin status route on staging and is a separate, approved step.

## Engine tenant isolation and the ownership boundary: what is tested, and what is not (2026-11-02)

**The question:** can any business access, mutate or infer another business's data through the engine's record references, relationships, operations or authorization boundaries? **The answer from the evidence: no path was found; that is not a proof that none exists, and it has NOT been shown on a real Durable Object.** The isolation is structural (each business is its own object with its own database; the engine reads and writes only `env.OFFICE_DB`, and references carry no business id because they need none) and, since Task 3, tested for the engine through the real front door.

### The layers, tested separately so one cannot hide a failure in another
| Boundary | What the test establishes | Suite |
|---|---|---|
| ROUTER (`routeRequest`) | an engine request goes to the business named by the session's signed claim; a client header, a target header or even a valid admin key changes nothing; forged, expired, altered or business-less sessions go to the Worker; `/admin/engine/*` needs the key AND a named, valid business | `engine-isolation.test.js` |
| OBJECT (one real `BusinessObject`, no router) | it refuses a session for another business, refuses a person who IS its member but whose session says another business (membership alone is not enough), and refuses a request that claims another business | same |
| FRONT DOOR (the Worker's real default-export `fetch` through the router into two real objects) | overlapping ids resolve to each business's own record; every relation and collection reachable from a record stays inside the business; an id that exists only in the other business is answered exactly like one that exists nowhere (status, body, headers); versions and metadata do not cross; refused operations write nothing in the other business | same |
| MISROUTE (the router made wrong on purpose) | an object bound to one business refuses another's request even for a person who is a member of both, and returns no data | same |
| OWNERSHIP (static, TypeScript parser, so comments never count) | R1 engine SQL names only engine tables plus `captures` in two named files; R2 no engine file references a shared binding; R3 engine imports are pinned; R4 only `capability-contract.ts` names an `eng_` table outside the engine; R5 the four legacy files that import the engine, and exactly what they import, are pinned; R6 who writes each engine table is pinned | `engine-ownership.test.js` |

The fixtures overlap on purpose (party 1, document 1 and payment 1 exist in both businesses with different content, and pending actions share ids), so nothing passes merely because ids are globally unique, and one person is an active member of BOTH businesses, so the session's business claim is the only thing separating them.

### What shows the tests can fail
`tools/engine-breakage.js` removes one tenant-boundary protection at a time (the router's use of the session, its signature check, the forwarding step's header overwrite, the object's session-business check, the object's one-business binding), each of which must fail the check that owns it, plus six ownership mutations. A COMPOUND control removes the router's, the session check's and the binding's protection together: the front-door suite then FAILS with a real leak (beta's data is returned to a request for alpha). That shows these checks catch that class of failure, not that every possible leak is detectable.

### Measured ownership (from the source, not assumed)
Fact tables are INSERT-ONLY across the whole source: no `UPDATE` or `DELETE` of any of them exists. They are written only by `engine/facts.ts`, plus one `INSERT INTO eng_event` for `operation.executed` in `capability-contract.ts`; `eng_interpretation` has no writer; the three mutable tables have named writers (`admin.ts`, `availability.ts`, `boundary.ts`, `drafts.ts`). Inside a transaction `atomic.ts` THROWS if code touches the AI, memory index, notes, vault, backups or shared database (`atomic.ts:14`), a runtime reinforcement for engine writes.

### FINDING, FIXED ON THE BRANCH AND VERIFIED ON REAL STAGING OBJECTS (not on production): an unused object bound to whichever business named it first
**The finding (misroute test, an object that had never been named):** alpha's request, delivered to it by a deliberately wrong router, was refused (no membership), yet the object had already saved `alpha-co` as its business; its genuine owner was then refused ("this object belongs to another business"). The binding was written before the request was authenticated, and the object never compared it with its own identity. No data was exposed (an unused object has none), but ownership could be taken and the real business locked out; it needed a router fault to happen, because the router derives the object name and the claim from the same id.
**The fix (`business-object.ts`, `types.ts`, `health.ts`; 12 insertions, 2 deletions):** an object is addressed by name (`objectNameFor(business)`, the one naming rule, used in only two places in `routing.ts`), and the runtime tells it that name, which no request can supply. A claim that does not match is refused 403 BEFORE anything is read, bound or written, so a request can no longer bind an unused object, or take one over, merely by naming a business. The invariant "a request cannot establish or change an object's business merely by naming one" now holds WHERE THE RUNTIME EXPOSES THE NAME. The object tells the pipeline its name (`OBJECT_NAME`) and `/admin/health` reports `object: { name, identityVisible }`.
**Fail-open, deliberately:** where the runtime exposes no name, or a value that is not a string, the object cannot know its identity and keeps the older first-claim binding as its only protection; a mismatch is never inferred from an unexpected shape, so no business can be locked out by the fix. Both behaviours are tested and labelled KNOWN LIMITATION, not as a security contract.
**Why this was safe to add:** the naming rule has been `business-<id>` since 2026-10-12 (stage 2b); before that a single object, `business-default`, was addressed, and it is no longer reachable by the router. Every reachable object's name therefore already equals its claim, so the check can only add protection.
**VERIFIED ON REAL STAGING OBJECTS (2026-11-02, staging only; commit `1ea2d45`, run 41580891686; record `ops/staging-identity-last.json`):** a read-only check (`tools/staging-identity.py`, run as the `identity` mode of `staging.yml`; GET only, no key printed, it reads nothing if staging is not running the commit under test) read `/admin/health` on the two real Durable Objects behind `staging-co` and `staging-two`. Both report `identityVisible: true` and a name exactly equal to `business-<id>` (`business-staging-co`, `business-staging-two`), so on the real runtime the object DOES know its own name and the check is effective. The staging gate run before it (41579574370, 48 of 48 steps) had every request to those objects pass through the new check with no false refusal, which rules out the unsafe case (a name exposed in a different shape would have refused legitimate claims).
**Still NOT established:** (1) PRODUCTION: this read staging's objects. Production is a separate Worker with its own objects, on the same platform and compatibility date (2026-07-01) but not read; after a deployment, `prod-health.yml` can read it. (2) The REFUSAL itself on a real object: a mismatched claim cannot be produced through the real front door without a router fault, so that behaviour is proven on the stand-in (the object, isolation and misroute suites) and inferred, not observed, on the real runtime. (3) Objects created or woken on a runtime that reports no name would still fall back to the first-claim binding (fail-open); nothing observed suggests this applies.
**Defence in depth was tested separately:** the first version of the tests let the object's older binding check be removed unnoticed, because the new check masked it (the breakage run caught that as a survivor); a test now exercises the binding layer alone on an object with no name.
**Related, from code only, untested, NOT addressed:** `/mcp` and signed-link requests are forwarded on an UNVERIFIED claim (`peekBusinessFromKey`, `peekBusinessFromToken`); the object verifies afterwards. A well-formed key naming any valid id therefore wakes, and binds, an object for that id (consistent with its name, so not an isolation failure, but an unauthenticated caller can cause objects to be created).

### What this does NOT establish
Real Cloudflare routing and a real Durable Object for the ISOLATION tests (the namespace there is a plain map and storage is a stand-in over Node's SQLite): engine isolation on a real object is unproven and would be a separate, approved staging step. Only the object-identity check above has been read on real staging objects. Flutter, MCP, the admin routes, file storage and signed links (their own mechanisms and legacy tests). Timing or other side channels, multi-query read consistency, and permissions WITHIN a business. Engine tables through migration and restore across businesses (the manifest check is tested, `backup.test.js:187`; an engine-specific test is not). The static rules cannot see SQL built at run time or access reached through a module the engine is allowed to import, and they describe the source, not runtime behaviour. ## Recovery hardening: the snapshot manifest is validated before anything acts on it (2026-11-02, Task 4 item 1)
**What the experiment showed (the real restore against a deliberately corrupted stored manifest, nine ways, 2026-11-02):** restore was mostly safe by design (everything is verified before anything changes, and the replacement is one transaction), but (1) a manifest missing `columns` for a table that no longer exists, or missing `fingerprint`, made restore REPLACE THE DATA and only then throw, so the caller was told it had failed after it had succeeded; (2) `version` was never read (a version 2 manifest restored); (3) one truncated or malformed manifest made `listSnapshots` throw for EVERY snapshot, which broke `GET /admin/backup/status` and `/list` and hid the good snapshots from the operator; (4) a part's key was never required to be inside the snapshot's own folder, so a manifest could point restore at another business's bytes (with a correct checksum). `ensureSchema` was found well defended (identifier checks, a single `CREATE TABLE IF NOT EXISTS`, no semicolon, column types checked). Likelihood is low (R2 writes whole objects and the manifest is written last); the realistic triggers are format drift, a bug in a later snapshot writer, or a hand edit.
**The fix (`backup.ts`, `backup-routes.ts`; tests first):** `validateManifest` (pure, never throws) checks EXACTLY what restore and listing use and tolerates everything else, so a good older snapshot is never made unrestorable by a stricter validator (unknown extra fields are tested as accepted): version 1, the tables (identifier names, no duplicates, sql, columns, row counts, parts), sequences, notes, files, the fingerprint, and that every part lives in the snapshot's own folder. `inspectManifest` returns one of ok, missing, incomplete or unreadable with a reason. Restore refuses an unreadable manifest ("cannot be trusted ... nothing was changed") BEFORE the lock, the safety snapshot, any schema change or any data replacement. Listing marks such a snapshot `unreadable` with its reason and still lists the rest; `GET /status` reports an `unreadable` count. The old meanings are kept: a manifest that is not complete, or names another business or snapshot, is still "no complete snapshot" and `readManifest` still returns null for it.
**Evidence:** `tools/backup-manifest.test.js` (68 checks: every corruption above, the two data-replaced-then-throw cases, forward compatibility, the cross-folder isolation case with a bucket-read log proving no byte of another folder is read, listing, and the three admin routes) and 14 breakage mutations, all caught.
**Not changed and not claimed:** the manifest still has no checksum of its own (an attacker or fault that rewrites a manifest AND its parts consistently is not detected; it needs write access to the backup bucket); no integrity verification is wired into restore (that would couple recovery code to the engine; the admin engine status route remains the way to verify after a restore); the recovery gate stays OPEN.

### Memory at size: a local PROXY, not a measurement of a Durable Object
One table of about 110-byte rows, Node, 2026-11-02: restore peaked at 37.5 MB heap and 22 MB buffers at 20,000 rows, 52.5 MB and 65.7 MB at 80,000, 96.5 MB and 121.6 MB at 160,000 (a snapshot, which a restore takes first as its safety snapshot, peaked at 28, 65 and 113 MB heap). Peak therefore scales with the LARGEST SINGLE TABLE, not a page, at roughly 6 to 7 times that table's JSON. A Durable Object's limit is 128 MB; whether a table of tens of thousands of rows is comfortably inside it is UNKNOWN, because the proxy differs from the platform in both directions. Closing it needs a ramp on a real staging object (not approved or run).

## Object ownership: how it is established, what is pinned, and what is recorded but not endorsed (2026-11-03)
**The principle (from the review of 2026-11-03):** provisioning CREATES identity, requests EXERCISE it, verification CONFIRMS it, and the three must not become interchangeable. The same applies to any future child object or storage partition: a newly provisioned object must not decide for itself which business owns it merely because a request supplied a business id.
**The lifecycle, from the code:** a business object is BOUND when its `object_meta` table holds a `business_id` row (cached as `this.businessId`); the binding is written once, by a plain `INSERT`, by the FIRST request that carries a valid `X-Business-Id`, before authentication and before anything but the runtime-name check. Both ways a business comes to exist create the directory row in the Worker's own database FIRST and then make an admin-keyed call into the object: the admin create-business route makes one `create-membership` call (or a `GET /health` for a migration target); sign-up makes four, the first of which, a READ-ONLY `membership-check`, is the request that binds. Every request reaches an object only through `idFromName(objectNameFor(id))`, so the runtime name is `business-<id>` by construction; Cloudflare documents `ctx.id.name` for that addressing (changelog 2026-03-15; it is undefined for `newUniqueId()`, `idFromString()` and names over 1,024 bytes).
**Pinned as INVARIANTS (tests, with breakage mutations):**
- STATIC (parsed from the source): the key is named in exactly three statements, all in `business-object.ts` (two reads and one plain `INSERT` that cannot overwrite); nothing anywhere updates or deletes `object_meta`; every other write to it is a keyed upsert; every meta-writer call (at least 15 are asserted) passes a literal key and none passes `business_id`; `object_meta` is in `SKIP_TABLES`, so snapshots, restore, fingerprints and the migration routes cannot touch it.
- RESTORE leaves the binding exactly as it was. On a REAL object, requests of every shape (the same claim, another business, with the admin keys, malformed, uppercase, missing, a lone target header) cannot create, change or reset it, with and without a runtime name; the alarm never binds.
- PROVISIONING, both paths, against real objects with a call log: the directory row exists before the object's first request, which carries the admin key and the server-derived id; the object ends bound to exactly that business under exactly `business-<id>`; a repeat leaves the binding unchanged; another business's claim is refused.
- Fail-CLOSED states: a MALFORMED stored value (empty, wrong shape, uppercase, padded) refuses every valid claim, rewrites nothing, and makes the alarm run no job and no backup while recording why; a MISMATCHED binding (stored alpha-co, runtime name business-beta-co) refuses both claims (alpha by the name check, beta by the binding check). Without a runtime name the stored binding is the only authority.
**Recorded, NOT endorsed (labelled OBSERVATION in the tests; each departs from the principle):** (1) an ordinary request still establishes ownership of an unbound object, where only authenticated provisioning should; (2) with no runtime name, an object whose binding row is gone is re-bound by the next valid claim, whichever business that is (with a name, only the matching business can re-bind it); (3) the hourly alarm checks only the stored binding, never the runtime name; (4) an UNAUTHENTICATED key naming a business that is not in the directory is refused yet creates and binds an object for it; (5) the object's first request in sign-up is read-only and still binds. Pinning these documents them without making them contracts: a change that closes one is expected and the test should then be updated.
**Evidence:** `tools/object-binding.test.js` (40 checks), 15 identity-state checks added to `tools/business-object.test.js` (89 in all), 6 breakage mutations, all caught in a selective run of the copy-based runner; no production source was changed. **Still open, and not decided here:** whether binding should be reachable ONLY through authenticated, directory-verified provisioning, and whether a name mismatch on a bound object should refuse (today) or be reported; the authenticated post-deployment health gate (designed in the review, not built); the staging rehearsal of that gate and of a rollback across migration `0004`; production's runtime name exposure and production's manifests (both unread); the recovery gate.

## The memory ramp on a real staging object: the tool (2026-11-08, owner-approved, staging only)
**Decided (Pierre, 2026-11-08: "Run the ramp").** The recovery gate's open question is how large a single table a real Durable Object can snapshot and restore before it runs out of memory (the limit is 128 MB; the 2026-10-28 failure was about size; the local proxy above says a restore peaks at roughly 6 to 7 times the largest table's JSON). No ramp tool existed, so this builds the smallest one, staging only.
**What was added, narrowly.** Two admin routes in `worker/src/engine/admin.ts`, both tier PRIVILEGED (both admin secrets), existing only where `ENGINE_REHEARSAL=1` (a staging variable production does not have), needing the business id as confirmation: `POST /admin/engine/ramp {confirm, rows}` tops up the marker rows in `captures` (`source = 'ramp'`, plain text of about 110 bytes, up to 250,000) and never removes any; `POST /admin/engine/ramp-clear {confirm}` removes exactly the marker rows. They touch the captures table and nothing else (the engine tables' hashes are unchanged by them). Tests: 20 new checks in `tools/engine-admin.test.js` (36 in all, red first: 11 failed before the routes existed), and `tools/admin-gate.test.js` now pins 177 admin routes and 43 privileged ones. The fill writes in statements of 20 rows and names no helper table, so the ownership rule R1 (the engine's SQL names only its own tables plus captures) still holds.
**How it is run.** `staging.yml` gained `mode: ramp`. It runs the usual shared steps (the deploy puts this branch's code, with the routes, on staging) and then, on `staging-two` only: for each of 20,000, 40,000, 80,000, 120,000 and 160,000 marker rows it tops the table up, takes a snapshot (`POST /admin/backup/run`) and restores that snapshot (`POST /admin/backup/restore`, which takes its own safety snapshot first), logging every call's HTTP status and seconds. The first failure ends the ramp (a failure is a RESULT, not a failed run), the marker rows are always cleared afterwards, and `tools/ramp-summary.py` writes sizes, statuses, seconds, whether each snapshot and restore reported ok, and a short error excerpt (no secret) to `ops/staging-ramp-last.json`, committed to the branch.
**What it will and will not show.** It shows the largest single table of this shape that a real object snapshotted and restored, and what the failure looks like if there is one. It does not show a mixed real workload, a table of different row sizes, or production. A call that fails at the edge (for example a proxy timeout on a long request) is recorded as what it is, a status and a time, and is read as such, not as a memory failure, unless its body says so.

## The memory ramp: result (2026-11-08, run 42524277585, staging-two only)
**RESULT: every size passed; the limit was not found.** The run (commit `061f061`, `mode: ramp`, recorded in `ops/staging-ramp-last.json`, record commit `57feb7d`) grew the marker table on the real `staging-two` object to 20,000, 40,000, 80,000, 120,000 and 160,000 rows (17.3 MB of text in the largest table at 160,000 rows, 160,223 rows in the whole snapshot). At every size the snapshot returned 200 (28.5 s at 20,000 rows to 33.8 s at 160,000) and its restore returned 200 with `ok` and no differences (46.5 s to 58.9 s), restoring the same number of rows. No call timed out or reported a memory failure, and the marker rows were cleared afterwards (160,000 removed, HTTP 200).
**What it shows.** A real Durable Object snapshotted and restored a single table of 160,000 rows of about 108 bytes, which the local proxy above had predicted to be near or over the 128 MB limit (96.5 MB of heap plus buffers); so on real Cloudflare the margin is at least that large and the proxy was conservative [inference: the proxy ran on Node, the object runs on workerd]. The slowest call, 59 seconds, was well under the proxy timeout that would have confounded a failure.
**What it does not show.** Where the limit is: the ramp stopped at 160,000 rows because that was the top of the ladder, not because anything failed. One table shape only (plain text rows of about 108 bytes in `captures`); a table of larger rows, or several large tables at once, was not tried. Production was not touched. The summary's per-size health field was read from the wrong key and came out empty (the health calls themselves all returned 200); `tools/ramp-summary.py` now reads the schema section the way the restore-proof judge does, for any later run.
