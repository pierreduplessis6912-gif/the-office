# System audit, Stage A part 1 (2026-10-31)

Work in progress: Stage A complete (parts 1 to 6); Stage B parts 1 and 2 (the customer journey, Meeting Mode, the dependency map and the verification plan).

Read-only. Audited commit: `42bcb74` (main; `6aff562` plus two docs-only commits). Production runs `8738923` (HANDOVER State, not re-verified today). ## Dependency map (Deliverable 3)
Measured from the source: how many files import each module, and how many files touch each table. "Excess responsibility" is my judgement from those measures, labelled as such.

**Layers, bottom to top**
1. Infrastructure: the Worker, one Durable Object per business with its own SQLite (`business-object.ts`), the shared directory database (`directory.ts`, 16 importers), the vault and backup buckets, the notes store, the memory index, the hosted model.
2. Contracts and gates: `types.ts` (76 importers), `auth.ts` (21 importers; sessions, capabilities, who may create or confirm what, route gate), `atomic.ts` (9; transactions), `refusals.ts` (8), `limits.ts` (7).
3. Record roots: `memory.ts` (7; capture first), `identity.ts` (12 importers; customers, people, characters), the schema (`schema-steps.ts`, baseline).
4. Interpretation: `ai.ts` (15 importers, 2,066 lines): split, extraction, image description, the conversation engine.
5. Orchestration: `index.ts` (4,205 lines, imports 61 modules: the routes and `processTranscript` and `processOneExtraction`), `intents/` (`opening`, `reply`, `lookup`), `scheduler.ts` (8).
6. Domain: `finance.ts` (4,352 lines, 16 importers): quotes, invoices, payments, orders, stock, PDFs, aged reports.
7. Interfaces: the app, the MCP endpoint (`mcp.ts`), the admin and debug routes (`debug.ts`, 2,537 lines, 25 modules).

**Table use (files that read or write it):** customers 12, characters 10, pending_actions 11, invoices 8, job_scopes 8, payments 7, quotations 5, captures 4, leads 4, stock_items 4, scope_components 3, snags 3, people 3, purchase_orders 3, customer_facts 3.

**High-impact components (a change reaches many domains)**
- `types.ts` and `auth.ts`: every intent, route and role passes through them. A new intent or action type without a permission row fails the build (F-018), which protects this.
- `ai.ts`: one extraction prompt and one model family serve every intent (F-011); a prompt edit can move behaviour in all of them.
- `identity.ts` and the `customers` table (12 files): a change to matching reaches leads, scheduling, stock, uploads and the pipeline (F-013).
- `finance.ts`: one file holds quotes, invoices, payments, orders, stock and the PDF; the VAT and balance questions (F-023, F-024) sit inside it.
- `pending_actions` (11 files): written in one place (F-019) but read and changed in many.
- Low reach, so a safer place to add evidence links: `captures` (4 files), `scope_components` (3), `snags` (3), `leads` (4).

**Single points of failure:** the model family for split, extraction and description; the one object that holds a business's data (restore not shown on production, F-021); the `BUSINESS_MODE` switch (F-006); sign-in sessions; `processOneExtraction` as the single path for spoken business changes.

**Excess responsibility (judgement):** `finance.ts` (4,352 lines across many domains), `index.ts` (routes and pipeline in one file, 61 imports), `debug.ts`.

**Existing mechanisms to reuse (all found in code):** capture-first (`logCapture`), the single hold point and per-type confirm rights, `job_scope_amendments` (field, old and new value, capture), the `project_ambiguity` and `identity_collision` questions, the current-customer register, `updateCaptureText` and `updateCaptureHint`, the server-side duplicate key, the generated route policy, the snapshot and fingerprint backup. `interaction_edges` is limited and fire-and-forget (F-030).

## Verification plan (Deliverable 8)

No test is named for a whole customer journey, a lifecycle or a scenario (searched by file name only). Coverage inside the large suites was not read.
