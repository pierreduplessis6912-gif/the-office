# System audit, Stage A part 1 (2026-10-31)

Work in progress: Stage A, parts 1 to 3 of the audit.

Read-only. Audited commit: `42bcb74` (main; `6aff562` plus two docs-only commits). Production runs `8738923` (HANDOVER State, not re-verified today). Nothing was changed in source, schema, workflows or production data. Order agreed with Pierre: audit the baseline, find gaps in current and proposed capabilities, build them, then the conversation and context layers, then the UX (`The_Office___the_orb_that_stays`, a mockup with invented data: one persistent orb, home, a list, one document, questions scoped to where you are, every answer tagged with its source, drafts confirmed by the owner). The front door fixes are parked behind this.

Evidence classes used: V-code (read in source), V-test (an automated test covers it), V-prod (checked in production), D (documented only), U (unknown). Everything below is V-code unless stated.

## Covered so far
Part 1: storage boundary, schema and cross-table links, the lead, snag and capture records. Part 2: how a typed or spoken message becomes a record (capture, split, extraction, capture link, duplicate protection). Part 3: customer identity matching, the two kinds of context, and the extraction-returns-nothing path (only partly traced). NOT yet covered: people and character matching in detail (`reconcilePerson`, `reconcileCharacter`), permissions, failure and recovery of uploads and background jobs, business arithmetic, the customer journey against the code, tests against operating conditions.

| F-012 | Duplicate protection: the server side is sound (`checkIdempotencyKey`, `auth.ts:944`: a row is written as processing before the work, a replay returns the stored result, a concurrent copy gets 409). The app's key is the text plus a 30 second bucket (`app/lib/main.dart:84`), so a retry after the bucket changes can write twice, and two identical genuine messages within one bucket collapse into one. A comment at the text route saying no client sends the key is stale: the app sends it (`main.dart:1002, 1167, 1253`). Other clients were not checked. | `auth.ts:944`, `main.dart:84` | Medium | Verified |
| F-013 | The customer matcher is loose in two places. For a name of two or more words, `reconcileCustomer` matches any customer whose name merely CONTAINS the spoken first word and last word (SQL `LIKE %first%` and `LIKE %last%`, `LIMIT 1`, no ordering), so "Ann Smith" can land on "Joanne Smithson". The whole-word helper is used only in the one-word branch. The name guard that asks about a near match sits in `intents/opening.ts:270` and covers ONE of the four callers; the other three reach the loose matcher unguarded: `scheduler.ts:535` (a sibling lead), `intents/stock.ts:51` (the job's customer in a stock usage) and `intents/upload-caption.ts:49` (a photo caption). An exact name, any case, now wins first (`identity.ts`). Read from code and SQL logic, not executed. | `identity.ts:363-430`, callers above | High | Verified by reading |
| F-014 | `customers.name` has no uniqueness rule; the table is `name NOT NULL` plus an optional `merged_into_customer_id` pointer. Duplicates can exist and an exact match picks the lowest id. HANDOVER documents two "mr peters" and says no merge tool exists in the MCP (documented, not verified by me). | baseline `customers` | Medium | Verified (schema), merge tool documented only |
| F-015 | Mentioning a new name creates a customer row at once (`reconcileCustomer` inserts and returns `matched: false`). The choice between customer and character rests on the extraction prompt's rule "does the tradesperson bill this entity", so a wrong call creates a customer without a hold. HANDOVER says undo does not remove a customer created this way (documented). | `identity.ts` insert branches; `ai.ts` prompt | Medium | Verified in code, undo documented only |
| F-016 | There are two separate kinds of context. (a) A server-side selection (`setSelection` after each resolved customer or character, `opening.ts`) used to resolve "he", "she", "the customer"; I saw the writes and did not trace every read. (b) The app's workspace context (room, report, period, selection), which is validated and recorded with the turn but, by its own rule, "not used to interpret speech yet" (`context.ts`). So nothing yet understands "where you are" in the app, which the orb design depends on. | `context.ts` header, `intents/opening.ts` | High for the UX stage | Verified |
| F-017 | When extraction returns nothing, the opening step is null-safe (optional chaining at `opening.ts:77, 120, 123, 150`). The path from there to a reply was not traced, so what a person sees for an unreadable message is unknown. | `intents/opening.ts` | Unknown | Open |
