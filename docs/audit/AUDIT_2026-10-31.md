# System audit, Stage A part 1 (2026-10-31)

Work in progress: Stage A, parts 1 to 6 of the audit.

Read-only. Audited commit: `42bcb74` (main; `6aff562` plus two docs-only commits). Production runs `8738923` (HANDOVER State, not re-verified today). Nothing was changed in source, schema, workflows or production data. Order agreed with Pierre: audit the baseline, find gaps in current and proposed capabilities, build them, then the conversation and context layers, then the UX (`The_Office___the_orb_that_stays`, a mockup with invented data: one persistent orb, home, a list, one document, questions scoped to where you are, every answer tagged with its source, drafts confirmed by the owner). The front door fixes are parked behind this.

Evidence classes used: V-code (read in source), V-test (an automated test covers it), V-prod (checked in production), D (documented only), U (unknown). Everything below is V-code unless stated.

## Covered so far
Part 1: storage boundary, schema and cross-table links, the lead, snag and capture records. Part 2: how a message becomes a record. Part 3: customer identity matching, the two kinds of context, extraction returning nothing (partly traced). Part 4: permissions and held actions, the people matcher. Part 5: backup and restore, the hourly job, how money is computed. Part 6: how balances and payments are summed, upload failures, how reads are gated. NOT yet covered: where an upload description finally ends up, supplier-side balances, the customer journey against the code (Stage B), and tests against operating conditions (no suite was run by me).

| F-013 | The customer matcher is loose in two places. For a name of two or more words, `reconcileCustomer` matches any customer whose name merely CONTAINS the spoken first word and last word (SQL `LIKE %first%` and `LIKE %last%`, `LIMIT 1`, no ordering), so "Ann Smith" can land on "Joanne Smithson". The whole-word helper is used only in the one-word branch. The name guard that asks about a near match sits in `intents/opening.ts:270` and covers ONE of the four callers; the other three reach the loose matcher unguarded: `scheduler.ts:535` (a sibling lead), `intents/stock.ts:51` (the job's customer in a stock usage) and `intents/upload-caption.ts:49` (a photo caption). An exact name, any case, now wins first (`identity.ts`). Read from code and SQL logic, not executed. | `identity.ts:363-430`, callers above | High | Verified by reading |

| F-016 | There are two separate kinds of context. | F-018 | Permissions are enforced in code at the boundary, and deny by default. `ENFORCE_APP_AUTH` is a source constant set to true (`auth.ts:427`), so no session gives no capabilities and an inactive membership gives none. Creating an intent is gated by a table typed so a missing row is a compile error, and confirming a held action is gated per action type (`ACTION_TYPE_CAPABILITY`, `auth.ts:496`; a type with no entry is owner-only). `ROUTE_POLICY.md` is generated from the real gate and checked on every build. The comment above `resolveCapabilities` still describes the old no-session-means-owner default and is stale. I did not run the role-matrix or route-policy suites. `ROUTE_POLICY.md` is stamped "Verified: not yet" and distinguishes only three of the 17 confirm types by name. | `auth.ts:148, 427, 490-535, 1059`, `ROUTE_POLICY.md` | Foundational (good) | Verified by reading; suites not run |
| F-019 | There is one place where an action is held: every held action is written by `holdForConfirmation` (`finance.ts:3532`, the only `INSERT INTO pending_actions`, `finance.ts:3540`), and the confirm route claims it atomically (`pending` to `processing` in one UPDATE, `index.ts:2374` onward) so two taps cannot both run it. | `finance.ts:3532-3545`, `index.ts:2374` | Foundational (good) | Verified |
| F-020 | The people matcher (`reconcilePerson`) is conservative: an exact name, then a whole-word match on the first word after any title; a name shorter than 8 characters or with a title is never auto-matched, and a sound-alike hit only ever becomes a question. The sound-alike pass scans the whole people table in code, which is fine at this size and grows with it. So two matchers answer the same kind of question with different strictness: this one, and the looser customer matcher in F-013. | `identity.ts:158-230, 363` | Medium | Verified by reading |
| F-021 | Backup and restore are built with care: a snapshot of every table, the notes and a file inventory, checksummed, in a separate bucket, 14 kept; a restore checks the checksums first, takes a safety snapshot, rebuilds, and compares a fingerprint (`backup.ts`). Production evidence is old: the last backup record is 14 Oct (47 tables, 2,006 rows, 129 files, healthy, 7 complete snapshots), so today's backup health is unverified. The only restore record (14 Oct) shows the guard REFUSING the request (the snapshot asked for was not the newest complete one; no restore ran), so a restore has not been shown end to end on production by these records. The memory index (Vectorize) is not in the backup, by the file's own statement. | `backup.ts`, `ops/production-backup-last.json`, `ops/production-restore-last.json` | High if untested | Design verified; production health and restore unverified |
| F-022 | Money arithmetic is done in code, not by the model: totals, VAT, deposit and retention are computed in `finance.ts`. But VAT is worked out when the PDF is drawn (`finance.ts:3866-3885`) from the business's current VAT settings and the customer's exempt flag, and the baseline has no stored VAT column; so a document drawn later could show a different VAT or total if a setting changed. Money is stored as floating-point `REAL` and rounded to two decimals at chosen points (`round2`, `finance.ts:1054`), not kept as whole cents. The balance question is settled in F-023. Only `invoicepool.test.js` has a money-related name; coverage inside the larger suites was not checked. | `finance.ts:155, 1054, 3866-3885`, `baseline-sql.ts` | Medium | Verified by reading |
| F-023 | The document and the ledger do not use the same figure. The invoice's stored `amount` is treated as the ex-VAT subtotal: for a flat invoice the PDF uses it as the subtotal (`finance.ts:3854`) and ADDS VAT on top (`finance.ts:3872-3882`), while aged debtors, balances and payments all work on the stored amount alone (`getAgedDebtorsReport`, `finance.ts:3018`; `allocatePayments`, `finance.ts:2987`), and no report adds VAT (outside the PDF code the only VAT references are two type fields). So for a VAT-registered business and a non-exempt customer, someone who pays the total printed on the PDF would leave an unapplied credit equal to the VAT in the ledger, and the debtors report would understate what the customer was asked to pay. It applies only when VAT is switched on; the production setting was not checked. For itemised invoices I did not confirm that the stored amount equals the sum of the lines. I read this and did not run it. | `finance.ts:2987, 3018-3040, 3854, 3872-3882` | High | Verified by reading; applies only if VAT registered |
| F-024 | Payments are not tied to an invoice or a job in the balance. Aged debtors adds up every invoice and every payment per CUSTOMER and applies payments to the oldest invoices first (`allocatePayments`); the `payments.invoice_id` column is not used by the report, and the report's own text says payments are not linked to a specific invoice. So a balance is customer-level, not job-level, which matters for the job-level continuity the Job Cards design asks for. | `finance.ts:2987, 3018-3036` | Medium | Verified |
| F-025 | Uploads keep the original but the pending description is never completed. A photo or document is written to the vault first, then a capture row is logged with the placeholder text "description pending" (`index.ts:3761, 3858`). A failure to describe an image does not lose the upload: `describeImage` catches its own error and returns text starting "[image description failed" (`ai.ts`), and PDF failures become a plain note. But nothing revisits a placeholder later (no code writes to it again), and the failure text is then used as if it were the description. Where the final description is stored, and whether a failure string can reach extraction as if it were real, was not traced. | `index.ts:3758-3806, 3858`, `ai.ts` `describeImage` | Medium | Verified; destination of the description open |
| F-026 | Strength: reads of restricted figures are gated in the lookup code, not by the model (20 capability checks in `intents/lookup.ts`, plus checks in `converse.ts`, `mcp.ts` and `opening.ts`), and `tools/lookup-hardening.test.js` with its breakage script exists. I counted the checks and did not run the tests or read each one. | `intents/lookup.ts`, `tools/lookup-hardening*.js` | Foundational (good) | Counted; suites not run |
