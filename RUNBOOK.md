# RUNBOOK: running The Office when something happens

Written 2026-10-14 for Pierre. Every command and route here was read from the code or run; the last section says, for each part, whether it has been **executed** or only written. Nothing here is a guess about how the system behaves unless it says so.

**The business:** `zululand-flooring-and-blinds`, on `https://office.websitehub.co.za`, one Durable Object per business (it runs in Paris, data centre CDG).

---

## 0. Set up once in Termux (the admin keys)

```
export OFFICE=https://office.websitehub.co.za
export BIZ=zululand-flooring-and-blinds
export ADMIN='<ADMIN_KEY>'
export CONFIRM='<ADMIN_CONFIRM_KEY>'
```

- **Read and write routes** need `-H "X-Admin-Key: $ADMIN"`.
- **Privileged routes** (restore, unlock, add a member, plans, merges, deletes, export) also need `-H "X-Admin-Confirm: $CONFIRM"`.
- **Anything about one business** also needs `-H "X-Target-Business: $BIZ"`.
- **Five wrong keys from one place lock that place out for 15 minutes**, even if the sixth is right. If you are locked out, wait; do not keep trying.
- The same two keys sit in GitHub as the secrets `PROD_ADMIN_KEY` and `PROD_CONFIRM_KEY`; the workflows use those, so for most things you never need the keys on your phone.

## 1. Every day: nothing

`Production health` (a GitHub workflow) reads the business every three hours (minute 7 of every third hour UTC: 02:07, 05:07, 08:07 … your time). It goes **red** when something that must happen on its own has stopped, and shows **warnings** for things worth knowing. Its last result is in `ops/production-health-last.json` (a verdict and counts, no secrets).

- Whether GitHub **emails** you about a red run depends on your GitHub notification settings (Settings, Notifications, Actions). Check that once.
- Run it by hand any time: GitHub, Actions, "Production health", Run workflow.

## 2. When the health check goes RED: what each message means and what to do

| It says | What it means | Do this |
|---|---|---|
| the health report could not be read | The Worker did not answer, or the admin key no longer matches | Run it again. Open `https://office.websitehub.co.za/health`: if that is not OK, see section 4 (a bad deploy). If it is OK, the `PROD_ADMIN_KEY` secret may have changed |
| the last hourly job FAILED: (reason) | The memory job failed. Customer data is **not** affected; memories are saved late | Read the reason. It retries every hour. If it keeps failing, check Cloudflare's status page (Workers AI, Vectorize) |
| the hourly job has never run and no run is scheduled | Nothing has armed the job | Open the app once (the first request arms it) and run the check again |
| the hourly job last ran N minutes ago | The job has stopped | Same as above; a new deploy also restarts it |
| the next hourly run is overdue (alarm stuck) | The alarm did not fire | Open the app once; if still overdue after the next check, deploy again (section 4) |
| the oldest memory has waited N minutes / N memories are waiting | The memory queue is backing up (the job or Vectorize is failing) | Fix the hourly job first. To push the queue by hand: `curl -s -X POST $OFFICE/admin/flush-memory -H "X-Admin-Key: $ADMIN" -H "X-Target-Business: $BIZ"` |
| server errors are X of the last N requests | Real failures are reaching members | Look at what changed: if a deploy just went out, go back (section 4). Otherwise read `GET /debug/timings` and Cloudflare's logs |
| the last backup attempt FAILED / the newest backup is N hours old / there is no backup | Backups are not happening | Run the "Production backup" workflow ("take one now") and read why it failed (the backup bucket `office-backups`, Cloudflare R2). **Do not ignore this one** |
| the daily backup was SKIPPED at (time): (reason) | The object could not even try its daily backup (no backup bucket bound, or it did not know its business's name). Found 2026-10-14: this happened after every restart until the bug was fixed | Read the reason. "No backup bucket" means the Worker's configuration lost the `BACKUPS` binding: restore it and deploy. Then run "Production backup" with `run` to take one now |
| a schema step FAILED / N schema steps are not applied | A database change did not apply. **Members get "This business is being updated" (503) until it is fixed** | Push a corrected migration, or revert the commit (section 4). After the fix: `curl -s -X POST $OFFICE/admin/schema/retry -H "X-Admin-Key: $ADMIN" -H "X-Target-Business: $BIZ"` (or wait: it retries hourly) |

## 4. Deploy, hotfix, rollback

**Deploy** = push to `main`. The pipeline runs, in order: typecheck, the whole test suite (twice: once on each database backend), a **staging gate only if a database migration changed**, the deploy, a smoke test of the live Worker. About 5 to 7 minutes. If the smoke test fails, it **rolls back to the previous version by itself**, smoke-tests again, and marks the run failed.

**Hotfix** = a small commit pushed the same way. Nothing skips the tests.

**Go back after a bad change** = revert the commit (`git revert <sha>`, push). Same pipeline.

**Do NOT go back to the old database by deleting `BUSINESS_MODE = "object"` and `LEGACY_LINK_BUSINESS` from `worker/wrangler.toml`.** That was a safe rollback only at the cutover on 2026-10-13. Everything written since lives in the business's object; the old database holds the data as it was at the cutover. Doing it now would show members stale data. Only consider it if the object itself is destroyed, and then restore from a backup first (section 5).

## 5. Restore from a backup

A snapshot of every table, the notes and an inventory of the files is taken automatically about once a day (when the newest is 20 hours old) into a **separate** bucket (`office-backups`); the newest 14 are kept. Files are mirrored incrementally.

**The easy way: the "Production restore" workflow** (GitHub, Actions, Run workflow). It needs no keys on your phone.
1. **List first.** Run it with both boxes **empty**: it only lists the snapshots (name, complete or not, rows, files, when) and writes nothing. This is the default, so a mis-tap restores nothing.
2. **Restore.** Run it again with the snapshot name in `snapshot` **and** the business id typed exactly in `confirm` (`zululand-flooring-and-blinds`). A small script decides first, and **refuses** (the run goes red, nothing is written) if the snapshot does not exist, never finished, the name has odd characters, the id is not typed exactly, or the snapshot is on the **deny list** (`ops/restore-denylist.json`: snapshots that are complete copies of a damaged business, each with its reason; the list shows them as `DENIED, NEVER RESTORE`). Restoring an older snapshot than the newest is allowed and is warned about, and so is a snapshot with under 90% of the rows of the largest one (it says how much it would lose). **If you ever see that a snapshot holds damaged data, add its name and reason to `ops/restore-denylist.json`.**
3. **What the restore does:** checks every checksum before changing anything; takes a **safety snapshot of the current state**; locks the business (members get "This business is being restored", retry in 60 seconds); then replaces the data **in ONE transaction, emptying tables children first and filling them parents first by the schema's foreign keys, so a restore that fails part way changes NOTHING** (true since 2026-10-14; before that it did not, see the decision log); then the notes and files; then checks a fingerprint. It is a **single attempt**: the workflow never retries a restore.
4. **To UNDO a restore**, run the workflow again with the **safety snapshot's name** (printed at the end of the run) and the id typed in `confirm`.
5. **Afterwards:** the run checks `/health`; then run "Production health" and check the numbers look right. The record is `ops/production-restore-last.json` (names, counts and statuses only).

**The manual way** (if GitHub is unavailable): `curl -s $OFFICE/admin/backup/list -H "X-Admin-Key: $ADMIN" -H "X-Target-Business: $BIZ"`, then `curl -s -X POST $OFFICE/admin/backup/restore -H "X-Admin-Key: $ADMIN" -H "X-Admin-Confirm: $CONFIRM" -H "X-Target-Business: $BIZ" -H "Content-Type: application/json" -d '{"snapshot":"<name>","confirm":"zululand-flooring-and-blinds"}'`. If the business stays locked after a failed restore: read `/admin/backup/status`, then `POST /admin/backup/unlock` (privileged) only once you know why.

**What a restore does not bring back:** the memory index (Vectorize), and there is no copy outside Cloudflare. **Point-in-time recovery** exists at Cloudflare (30 days for SQLite-backed objects) but **nothing in the Worker lets you trigger it**, so it is not available to you today.

## 6. The model provider is down

Every model call is tried 3 times (waits of 0.3 s then 0.6 s). If it still fails, each feature falls back instead of crashing, and the failure is logged. What a member sees, from the recorded test cases: when the second-stage reading fails on an invoice sentence, **the invoice is still noted and held for confirmation**, and the reply says it could not read the job details and to say that part again. **What was never observed:** a total provider outage end to end.

- **Check:** Cloudflare's status page (Workers AI); the health report's model failure counts (`GET /admin/health`).
- **Tell members:** say the job part again later; held actions are not lost.
- **Nothing to switch off.** If it drags on, do the cost-spike steps only if spend is rising (section 7).

## 7. A cost spike

A message costs about 940 neurons (about $0.01). Free allowance: 10,000 neurons a day for the whole account; after that $0.011 per 1,000.

- **See it:** the production health check warns above a dollar figure and at 80% of the day's ceiling; `GET /admin/health` shows today's model use.
- **The ceiling is a real stop.** Plan `standard` is in **enforce** mode (since 2026-10-14): 100 messages per member per day, 400,000 neurons (about $4.40) per business per day. Over either limit, the member sees "You have reached today's limit of 100 messages. It resets at midnight UTC" (or the business version). **Midnight UTC is 02:00 your time.**
- **Lower the limits fast:** GitHub, Actions, **"Production plan mode"**, Run workflow: set the two numbers (whole numbers) and keep `enforce`. It takes effect within 5 minutes. It reads the result back and records it in `ops/production-plan-last.json`.
- **Switch to warn (record only, never block):** the same workflow with `warn`.
- **The app needs the Codemagic rebuild** (done?) to show the friendly limit message; until then a member who hits a limit sees "Something went wrong".

## 12. Creating a new customer's business

A business is created by **you**, not by self-serve sign-up (decided 2026-10-14). It needs three things: a **business id** (3 to 40 lower-case letters, digits and hyphens, for example `acme-floors`), the **business name** as it should appear, and the **owner's Google email**, the account they will sign in with.

1. GitHub, Actions, **"Production new business"**, Run workflow. Fill the four boxes: the id, the name, the owner's email, and **the id again** in `confirm`.
2. It first **reads** the directory and asks whether that email already belongs to a business. A small script then decides. It **refuses**, before any write and with the run going red, when: the id is not valid or is reserved (`admin`, `api`, `app`, `auth`, `debug`, `demo`, `health`, `office`, `staging`, `test`, `www`, or starting `staging-`); the name or email is not valid; the id is not typed again exactly; **the email already belongs to another business** (one email can sign in to only one business; it does not say which); or **the business already exists and already has members** (so a typed id can never add a second owner to a live business; to add someone use `add-member`, section 8).
3. If it is allowed, it makes **one** attempt to create the business on the `standard` plan (100 messages per member per day, 400,000 neurons per business per day, enforced) with the owner as its owner. It then checks the result: the business is in the directory, active, on the standard plan; the owner is a member; its own object answers **as itself**. A failed check turns the run red.
4. **If it stops half way**, run it again with the **same boxes**: a business that exists with **no** members is completed; one that has members is refused.
5. Then tell the owner to install the app and **sign in with Google using exactly that address**. Their journey (business details, customers, invoices, team, suppliers, materials) starts the first time they open it, and each import step takes a spreadsheet.

**The owner's email is personal data and this repository is public, so it must never reach a log.** GitHub prints every step's `env:` block in its log, so the workflow keeps the email OUT of the environment and every expression: its first step reads it from the event file, registers it as a mask (any later print shows `***`) and writes it to a file the other steps read. The summary shows it only as `o***@acme.co.za`; the record (`ops/production-new-business-last.json`) holds the business id, its name and statuses only. **Verified, not assumed:** the first version had the email in the environment and it appeared 10 times in one run's logs; after the fix a canary address appears 0 times in 11 log files (the tool below). **Never type a real email address into the leak-check workflow.** It is a check for PLACEHOLDERS.

**What it does not do:** it sends no invitation (you tell the owner); there is **no workflow to delete a business**, so a business created by mistake stays as an empty business until Claude removes it by hand; and a new business's object is created from a GitHub runner, so it is placed wherever Cloudflare chooses for that first request (the Paris finding in section 3 applies; not felt so far).

**Executed?** The guard and the workflow's structure are tested (88 checks, 14 breakages caught). The create route it calls has run on **real Cloudflare** for two businesses in every staging rehearsal. **The workflow has been run in production for its two safe paths (2026-10-17):** asked to create the live business `zululand-flooring-and-blinds` it read the real directory, saw 4 members and REFUSED (the create step was skipped, nothing written); asked to create a valid new business with a mistyped confirmation it REFUSED the same way. In both runs the record held no email. **The creating path has now run once in production (2026-10-17): it created the test business `tender-hub` ("Tender Hub", owner `t***@gmail.com`, Pierre's own second account).** Every step passed; the guard approved; the create answered 200 (`created`, `ownerInDirectory`, `ownerMembershipStatus` 200); the post-checks passed (in the directory, active, standard plan, the owner a member, its own object answering as itself); an independent check afterwards showed the live business still at 4 members and Tender Hub at 1. **`tender-hub` is a TEST business and stays in production until it is removed by hand** (there is no workflow to delete one).

### Checking whether something appears in a run's logs

`Log leak check` (GitHub, Actions, Run workflow): give it a run id (the number at the end of a run's URL) and a **placeholder** string; it downloads that run's logs **from inside GitHub** (this environment cannot) and records how many times the string appears, with control counts (so zero means "read the logs and it is not there", not "read nothing"). Counts only, in `ops/log-leak-check-last.json`. The needle is an input of that workflow, so it is visible in that run: use only a made-up address, for example `canary-123@example.com`, and test a new workflow by running it with that canary first.

**The trial.** 14 days. Small limits, always enforced: **30 messages per person per day and 60,000 neurons per business per day** (about 64 messages, roughly $0.66 a day, so one trial costs about $9 at most). Their session ends when the trial does. ## 15. Bringing a trial back (convert to a paid plan, or extend)

When a customer's 14-day trial ends, the owner can no longer sign in (they see "please contact us"). To answer them: GitHub, Actions, **"Production trial"**, Run workflow. Boxes: the **business id** (find it in `GET /debug/directory`: it is the name's slug plus six characters), the **action** (`extend` or `convert`), **days** (extend: 1 to 90) or **plan** (convert: for example `standard`), and the **business id again** in `confirm`.

- **extend** gives the trial N more days, counted from the LATER of now and its current end, so an ENDED trial comes back to life for exactly N days from today, and one still running gets N added. It stays on the trial plan.
- **convert** moves the business to the plan it pays for and clears the trial, so the owner signs in as a normal member (a normal 30-day session, the plan's limits).

It first reads the directory and the plans; a tested guard then **refuses**, before any write and with the run going red: a bad id, a mistyped confirmation, a business that does not exist, is not active (pending or suspended) or is **not on a trial** (an operator's business, or one already converted), a plan that does not exist or is `trial` itself, or days outside 1 to 90. If allowed it makes ONE attempt, then checks (a convert shows the plan and a cleared trial; an extend shows a later end by at least the days asked) and the run goes red if not. Only ids, plan names and numbers pass through: no personal data. After it, **ask the owner to sign in again** (their old session ended with the trial). Nothing is ever deleted.

**Executed:** the route on the REAL staging database in the rehearsal (refused without the confirmation key; extend moved the end by exactly 7 days; convert cleared it and set the plan; a repeat convert 409; an unknown action 400), and in the tests (including an ENDED trial brought back by extend and by convert). **Executed in production (2026-10-17):** the first real signup's test business had its trial extended by ONE day through the workflow: every step passed, the route answered 200, and the directory showed the end date move from 2026-10-31 18:49:18 to 2026-11-01 18:49:18 with the business still on the trial plan. **Not executed in production:** convert, and bringing back a trial that has actually ENDED (proven in tests and on the real staging database, not on a real ended trial).

## 16. When CI fails and you cannot see why

GitHub's logs are not reachable from where Claude works. **"Log excerpt"** (Actions, Run workflow, a run id, default step name `Role-matrix`) reads that run's TEST step from inside GitHub and records the failing lines and the last lines in `ops/log-excerpt-last.json` (it refuses a deploy or secret step; output is capped). **"Log leak check"** counts a PLACEHOLDER string in a run's logs (never a real address: the needle is a public input).

**Two things to know about the pipeline.** (1) **The deploy decision asks PRODUCTION what it is running** (fixed 2026-10-17; it used to ask "did the Worker change since the previous commit?", so a red run followed by a tests-only fix silently skipped the deploy and a migration's staging gate). The deploy stamps its commit into the Worker (`wrangler deploy --var GIT_SHA`), `/health` reports it (`{"status":"ok","service":"office-api","commit":"<40 characters>"}`), and the pipeline asks it before every push (`tools/deployed-base.sh`), then deploys if the Worker or the deploy workflow changed SINCE THAT COMMIT, and gates if a migration did. **When production's answer is missing, malformed, not in this history or not an ancestor, it deploys and runs the staging gate** (when in doubt, do the safe, slower thing), so the first push after an old Worker, or a transient network failure, costs a gate run and nothing worse. A manual run of the deploy workflow still always deploys and is never gated. To see what production runs: open `/health`, or run **"Production signup check"** (it records `running_commit`). **Proven on the real pipeline:** a deliberate drill (a red commit with a Worker change, then a tests-only fix) deployed the Worker change, and production then reported the fix's commit. (2) Any workflow that records its result by pushing must push to `$GITHUB_REF_NAME`, never `main`: from a branch it would otherwise push that branch's unmerged code to `main`, which deploys to production (three staging record steps and the leak check had this; all fixed and pinned).

### The empty-business handover, 2026-10-18 (`ee69977`)

**The problem.** An employee who signed up for their own trial by mistake has an address bound to that empty business, so adding them to their employer's business was refused ("belongs to another business"), and signing in took them straight to their own empty business: they never saw an invitation.

**What happens now.** The owner INVITES them (a direct add of such an address is still refused, now pointing at inviting instead). When that employee signs in with Google in a browser, and ONLY if their own business is **self-started, still on its trial, has exactly one member (them), and is verifiably EMPTY**, and they have a pending invitation to another business, the sign-in page ASKS them: **Join X (your empty business is closed; nothing is deleted)** or **Keep my own business**. Keep declines the invitation, so they are not asked again. Join closes the empty business (`status = closed`, `closed_into` = where they went: the only record of it), binds their address to the new business, creates the membership recording who invited them, and accepts the invitation. **Nobody can do this to them: it needs their tap, and the server re-checks everything when they tap** (a tampered form, a stale page, an invitation withdrawn meanwhile, or data added meanwhile all just sign them in to their own business with nothing closed). The order makes a failure part way recoverable (membership, close, move the address, accept): if it stops after the old business closed, the same person's ordinary Join finishes it, because **an address bound only to a CLOSED business conflicts with nothing and simply moves**. **Inviting is now neutral**: an address in another business is invited exactly like any other, and the owner learns nothing about it either way (refusing used to reveal that the person already has an account); for anyone who is not eligible the invitation just waits and expires.

**What "empty" means (emptiness.ts, asked of the real object by `GET /debug/emptiness`, a read-tier admin route).** Measured, not guessed: a business database has 42 tables and right after signup exactly TWO hold a row (memberships: the owner; business_profile: the name). Empty = every other table has no rows, the only member is the person asked about (an ACTIVE OWNER), and the profile holds nothing but a name. **Four tables are written by the PLATFORM for every real business and are ignored: `object_meta`, `schema_steps`, `admin_audit` (every privileged call is audited inside the object, and signup itself makes two) and `request_timings` (RECORD_TIMINGS is on in production).** Everything else counts, including any table a future feature adds, so the rule can only err on the safe side. **Two tests keep it honest: one puts a row in EVERY table and requires the answer to flip, and one FAILS if anyone adds a lazily-created table without classifying it as platform bookkeeping or owner data.**

**What it does NOT do.** It never merges data: a business with anything in it is never offered (those people use another Google account, or an operator sorts it out). It does not handle a person who is a MEMBER (not the owner) of a business, or an owner with several members.

**Executed.** Tests: 28 emptiness checks, 43 handover checks in the sign-in tests, 14 breakages caught; both backends 6,606. **The REAL staging objects, 38 of 38**: an employee with an empty business who agrees joins and the empty one is closed; one whose business holds data is never moved (signed in to their own); one who keeps theirs has the invitation declined; and inviting an address in another business reveals nothing. ### Quoting as its own capability (`can_make_quotes`, "Quotations"), 2026-10-18 (`19c73f9`)

**What it is.** A salesperson can now dictate a quotation, confirm it, edit it (`PATCH /quotations/:id`) and send its PDF link, WITHOUT being able to confirm payments, raise invoices, convert a quote into an invoice, or see any money. The quotation rules check the new capability ALONE, so the switch is real: an owner can take quoting away from an accountant without taking money away, give an installer ONLY quoting, or switch it off for sales, all from the existing permission screen (a new "Quotations" row).

**Nothing changes for anyone until an owner flips it.** Quotations FOLLOW "Money in and out" until set on their own (`INHERITED_FROM`, the precedent of 2026-10-04 for expense totals and supplier balances), so an accountant, admin or installer who had money could quote and still can, and one whose money was switched off still cannot. **Only sales is independent**: its default has quoting without money.

**Still money-only, deliberately:** `price_scope` (pricing a measured scope can produce an INVOICE), `convert_quote` (a quote into an invoice), invoices, payments, expenses, editing an invoice or a customer, and the finance list. So **sales quote with the plain "quote ..." phrasing; "price this scope" is still refused for them**, and **sales have no list of quotations**, only the link they get when they confirm one. Not exercised with a real dictated quote as a salesperson: the real rehearsal proves the gate and the switch, not a quote end to end.

**Two traps found before building, and why they are pinned.** (1) **"Follows its parent" strips a child its role has without the parent**: the old rule removed the child when the parent was absent, which would have silently removed quoting from sales; and the permission screen's "is this the default?" compared with the PARENT'S state, so switching quoting off for sales would have been treated as "back to default" and never stored. One shared helper, `followsParent(role, capability)`, now decides it for both the loader and the switch, and a role is independent ONLY when its static default has the child WITHOUT the parent (sales). My first version of the rule ("independent if the child is on by default") would have stopped the accountant's quoting from following money; the tests written first caught it. (2) **The "keep this sentence out of free-text notes" rule is DERIVED from the capability** (`intentKeepsOutOfNotes`: an intent whose creation needs money). Notes bypass every gate and are read back to anyone who looks the customer up, so moving quotations to a new capability without updating that rule would have put dictated quotes (customer and price) into notes an installer reads. It now counts either capability, and `tools/quotes.test.js` pins the full list of 25 intents recorded from the code BEFORE the change.

**Executed:** 43 quote checks (every role's real ability, every owner switch with persistence and audit, the split gate rules), 13 breakages caught, both backends 6,659; the REAL staging object, 42 of 42 (sales may edit a quotation but not an invoice or a customer, an installer may not quote, the owner switches quoting off and on for sales and it persists, installer-only quoting then reset); production runs the commit (probe 9 of 9). ### A person for every login, and a profile for each person, 2026-10-19 (LIVE: server `821a635`, screen `75b5fc8`)
